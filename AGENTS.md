# Instructions for coding agents

This repository is an EPFL SwEnt Android team project. Read this file, the
project README, the relevant issue, and nearby code before making changes. The
team owns every change, including code written with AI. Keep each change small
enough for a teammate to understand and review.

## Project structure and architecture

- Use Kotlin and Jetpack Compose. Follow the existing package layout, naming,
  dependency versions, navigation setup, and formatting rules. The starter may
  be the team's bootcamp project or the SwEnt Android-Sample; inspect the actual
  repository before assuming a class, module, backend, or Gradle task exists.
- Follow MVVM: Compose screens display observable UI state and forward user
  actions to a ViewModel. ViewModels own screen state and coordinate operations.
  Models and repositories own domain data and data access.
- Put Firebase, Supabase, HTTP, and persistence code behind repository
  interfaces. Do not import a backend SDK in a ViewModel or a Composable. Inject
  dependencies so the data layer can be tested with fakes.
- Keep long-running work off the main thread. Use coroutines and expose
  lifecycle-aware observable state (such as `StateFlow`) according to the
  surrounding code. Represent loading, empty, success, and error states where
  relevant.
- Handle invalid input, network failures, and loss of connectivity. Preserve
  useful offline behavior required by the product; if the team chooses
  Supabase, plan explicit local caching where needed.
- Keep the SwEnt product requirements in view: a public cloud service, user
  authentication, a phone sensor used in a core feature, and useful offline
  behavior. Do not introduce a custom backend without the instructor's written
  approval.
- Do not change generated files, Gradle wrapper binaries, or bootcamp
  `sigchecks/` (if present) to make a test pass. Do not weaken existing tests.
  Ask the team to resolve an interface or product decision that the issue does
  not specify.

## Backend and configuration

- Follow the backend actually selected by the team. Keep setup instructions in
  the README so every teammate can clone, configure, and run the app.
- An Android client API key or Firebase `google-services.json` may be committed
  when it contains only client configuration. Such keys are identifiers, not
  authorization: enforce access with Firebase Security Rules or Supabase Row
  Level Security, and test the rules for unauthorized access.
- Never put private keys, service-account JSON, signing credentials, or a
  Supabase `service_role` key in the app or repository. Keep server-side secrets
  in an appropriate secret manager or CI secrets. Enable RLS on every Supabase
  table and give the Android client only the publishable/anon key.
- Prefer emulators or test doubles for backend tests. Never make unit tests
  depend on a live production backend.

## Build and tests

From the repository root, use the checked-in Gradle wrapper (on Windows
PowerShell, substitute `./gradlew.bat`):

```bash
./gradlew ktfmtCheck
./gradlew check
```

`check` runs local checks and unit tests; it does **not** replace Android
instrumented tests. When a change affects UI, Android integration, or backend
integration, start an Android emulator/device and any required local backend
emulators, then run:

```bash
./gradlew connectedDebugAndroidTest
```

For the Android-Sample starter, CI also runs `./gradlew assemble lint`,
`./gradlew connectedCheck`, and coverage. Check the actual `.github/workflows/`
files for this team's required gates. If a command cannot run locally, report
the command, error, and which checks remain unverified; do not claim it passed.
Write tests for behavior and edge cases, with meaningful assertions. Put JVM
tests under `app/src/test/` and device tests under `app/src/androidTest/` when
that layout exists.

## Branches, commits, and pull requests

- Start from the current `main` and work on a branch for one issue or focused
  change. Do not push directly to `main`. Keep unrelated refactors out of the PR.
- Commit small, coherent steps and push the branch regularly. Use an English,
  imperative, capitalized subject of at most 50 characters, for example
  `Add offline task cache`. Add a blank line and a body explaining *why* when
  the subject is insufficient; wrap body lines around 72 characters. Reference
  the issue when applicable. Do not mix this convention with lowercase
  Conventional Commit subjects unless the team explicitly adopts that style.
- Keep Git commits under the human team member's existing Git identity. Do not
  change `user.name` or `user.email` to an AI identity, add an AI
  `Co-authored-by` or other contributor trailer, or include automatic
  "generated by AI" signatures in commit messages. Acknowledge substantive
  AI contributions in the affected files as described below, not as Git
  authorship or co-authorship.
- Open a PR with the issue, behavior, tests run, and any setup or limitation.
  Feature code and its tests belong in the same PR, even if committed
  separately. Use a draft PR for work in progress.
- Request at least one teammate's substantive review in English. Merge only
  after approval and required CI checks pass, following branch protection.
  An AI review can help, but the teammate must still understand the diff.

## Acknowledging AI and other sources

- When AI or another external source contributes to a source file, add or
  update a comment at the **top of that file** naming the contributor/source
  and the contribution. Use a short, truthful description, for example:

  ```kotlin
  // Contributors: OpenAI Codex (drafted repository tests); Jane Doe (reviewed and revised).
  ```

- For Markdown or configuration files that allow comments, use the appropriate
  top-of-file comment. If the format does not allow comments, document the
  contribution in the PR and another suitable tracked file. Do not invent
  human reviews or claim that AI output was written independently.
- Human contributors must read and understand every submitted change and be
  able to explain its design, behavior, tests, and review comments.

## Agent workflow

1. Restate the issue's goal and acceptance criteria; inspect the smallest
   relevant part of the codebase and existing tests.
2. Implement one reviewable change consistent with the current architecture.
   Keep the diff focused and add or update meaningful tests.
3. Run the applicable commands above, inspect failures, and fix their causes.
4. Review the diff for accidental files, leaked credentials, missing contributor
   acknowledgments, error handling, and actual test assertions.
5. Report what changed, which checks passed, and any remaining limitation in
   the PR. Leave the final code review and merge decision to the team.
