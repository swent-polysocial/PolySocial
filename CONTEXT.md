# Project context

What a coding agent (or a new teammate) needs to know before starting a session and can't easily get from the code: the current state, the decisions that override older text, and the traps. Process rules live in `AGENTS.md`, the design in the wiki's [Architecture Diagram](https://github.com/swent-polysocial/PolySocial/wiki/Architecture-Diagram) (source: `docs/Architecture-Diagram.md`). **Keep this file short.** Only add what changes how someone should build things (see "Session context" in `AGENTS.md`).

## Current state

- **Groups/chat privacy (#241):** both offline notices describe membership, live chat and retained text/time after deletion. `deleteAccount` clears message sender links across all chats before memberships and Auth; retry preserves completed work. Deleted tokens cannot start/join groups, recreate markers or read/send messages. See `docs/Group-Chat-Deletion.md`.

- **Package** `com.polysocial`, minSdk 28, compile/target SDK 37, JVM 17. - **Security Rules** (`firebase/firestore/firestore.rules`) **deny everything by default**; collections and event subcollections not listed here stay denied. Emulator config is in `firebase.json` (Auth 9099, Firestore 8080).
  - `users/{uid}` (#35): owner-only for verified emails, `isAssociationVerified` protected; `uid` matches the document ID, `accountType` is `student` or `association` if set, and both are fixed after creation; `displayName`, when present, is at most 50 UTF-16 units (#143, the app's `MAX_DISPLAY_NAME_LENGTH`). An association can't delete its own `users/{uid}` (it would then count as a student, #161); an admin deletes association accounts.

  - `events/{id}`: students read public events and private ones listing them in `allowedUids` (#52); a verified association reads only its own association events (`createdBy == auth.uid` and `isAssociationEvent == true`). Verified students and verified associations create with `createdBy == auth.uid` in `organizerIds`, every organizer also in `allowedUids` (so no co-organizer manages a private event they can't read), and `validateNewEvent`'s title, description and category limits plus an optional `locationName` of at most 100 characters (#47, #102). A verified association always sets `isAssociationEvent` and no one else may, because its read rule only covers its own association events. Any organizer updates or deletes; `createdBy` and `isAssociationEvent` are fixed once created.
  - `associations/{uid}`, `publicProfiles/{uid}`, `deletedAccounts/{uid}`, attendees, groups, `groupMembers` and the groups' chat messages (#237): see their entries under Decided design (and the Architecture Diagram's rules table).

## Decided design (follow this, even where an issue still says otherwise)

Closed issues keep their original text, so where one disagrees with this section, this section wins (for example, #31 still names a shared `AuthViewModel`).

### Architecture

- **Layers:** Compose screen → ViewModel (one `StateFlow` UI state) → repository interface → Firebase/device implementation, with a `Fake…` implementation for tests (`app/src/sharedTest`). Pure logic (validation, haversine distance, filtering, matching, QR parsing) goes in plain Kotlin with no Android/Firebase imports. Every screen that holds state has exactly one ViewModel (e.g. `LoginViewModel`, not a shared `AuthViewModel`); the app shell has none, because the `NavController` owns navigation state.
- **Failures** follow `AGENTS.md` → Architecture: typed `…Result`s (`NetworkError` / `UnexpectedError`) shown as an error state with a way out, a test per failure path; a cancelled Firebase task while the caller still runs is a failure (`reportFailures`, `model/user/FirestoreFailures.kt`).
- **DI: Hilt** (#70, chosen after review over manual DI because it scales as repositories grow): `@HiltViewModel` with constructor injection, `hiltViewModel()` in Compose, one Hilt module per feature; tests replace repositories with the `Fake…` versions through Hilt test modules. `FirebaseModule` (`model/firebase`) resolves the current `FirebaseFirestore` from `FirestoreSession`; repositories take a provider so they use the replacement after a cache clear.
- **Time:** classes that need the current time take a `java.time.Clock` from `ClockModule` (`model/time`, unscoped, so each injection reads the device's current time zone); tests pass a fixed clock.
- **Offline** relies only on Firestore's offline cache. No Room, no map tile prefetching, no Mapbox offline region downloads.
- **Not built yet:** an action Figma shows but the app doesn't support yet shows a "not available yet" Snackbar, never a broken screen (Milestone M1 requires the app not to misbehave).
- **Shared UI parts live once in `ui/common`** (`FormParts.kt`, `LoadingState`, `ErrorState`, `StateButton`, `ConfirmationSheet`…): reuse or extend them instead of copying a field label, banner, button or sheet into a screen (M1 coach feedback, [#251](https://github.com/swent-polysocial/PolySocial/issues/251); see `MODULARITY.md`).
- **Category look:** `ui/event/EventCategoryStyle.kt` gives each `EventCategory` its icon, label and colors (Figma: party red, sports green, culture blue, study amber; Other neutral). Reuse it instead of a second mapping, and show the label next to the color (Figma: never color alone).

### Navigation

- **One `NavHost` in `AppShell`**, with string routes defined in the `Tab` enum (no typed routes, so no serialization plugin). Each tab is a nested graph (`tab.route`, starting at `tab.rootRoute`) with its own back stack (#42); switching tabs uses Android's standard pattern (`popUpTo` the start destination with `saveState`, `launchSingleTop`, `restoreState`), so a tab comes back on the screen it was on.
- **Back:** at the root of the Map, Chats or Profile tab, back goes to the Events (home) tab, and at the Events root it exits (Android's standard). This overrides #42's text.
- **Routes inside each tab:** `tab.eventDetailRoute` (#112) for every event (Events cards, "View event", the map preview's Details), `tab.editEventRoute`, `tab.findGroupRoute`, `tab.createEventRoute` (#110) and a placeholder `tab.detailRoute` that events never use.
- **App bar actions (#84):** a tab's `TabAction` (Events → notifications, Chats → search chats, Profile → edit profile; Map has none, as in Figma) shows **only at the tab root** and opens `tab.routeOf(action)`, a placeholder until its feature replaces it at the same route. No unread dot until notifications exist.
- **Tab loading state:** each tab root shows the shared `LoadingState` until its content is ready, with no artificial delay; placeholder tabs use `PlaceholderTabViewModel`, scoped to the navigation entry, so it shows only on a tab's first visit. Errors use the shared `ErrorState` (Figma "Tab · couldn't load").

### Sign-in and accounts

- **Sign-in providers: email/password and Google only, no Microsoft** (#106, #107; Lucas, [#197 review](https://github.com/swent-polysocial/PolySocial/pull/197#pullrequestreview-5539093813)). Microsoft sign-in would need EPFL's admin to whitelist the app, which is unlikely (they haven't for Canva). Google is open to every app and goes through EPFL's SSO, so it proves ongoing ownership of the `@epfl.ch` address just as well. Students still need a verified `@epfl.ch` email (the rules check it); only email/password needs our Verify Email screen.
- **Google sign-in (#106, #107):** Credential Manager explicit button flow, with Firebase token validation and a verified, exact `@epfl.ch` check before profile access; other domains (uppercase domains and subdomains too, to match the rules; the identity isn't normalized) are rejected before Firebase creates an account. The owner confirmed Firebase's automatic provider linking for EPFL Google accounts through EPFL SSO: use the returned UID, with no collision outcome, client-side linking flow or original-method error screen. New Google users enter the profile step with name and email prefilled; existing users go through the startup profile check. Cancellation is silent, but only a real dismissal counts as one (#319, see Traps): a Google failure reported as a cancellation shows the generic error; unexpected failures offer Try again; error screens use two columns in wide, short windows and Back returns to the original auth screen. Tokens and rejected identities are transient only. OAuth and SHA-1 setup: README "Google sign-in setup" (a config without a Web OAuth client fails compilation on `default_web_client_id`); Google sign-in from the CI APK uses the stable CI certificate registered in Firebase (#383).
- **Google sign-in buttons:** Welcome and Log in share the unchanged pre-approved Google PNG through `GoogleSignInButton`, preserving the logo, font and aspect ratio ([Google requires compliant branding](https://developers.google.com/identity/branding-guidelines) for app verification; a plain-text or monochrome G is not allowed). The light pill is our chosen variant, not a Google requirement. Both actions run the same repository operation and disable competing navigation while loading.
- **Password recovery (#164):** the owner keeps email enumeration protection enabled. Request resets directly through `AuthRepository`; never fetch providers by email. Every accepted request shows the same conditional inbox guidance, including unknown and Google-only addresses; this supersedes the provider-aware prototype, whose Figma missing-account/provider states are archived, not implemented. Signup may still show duplicate-email feedback. The request preserves the auth session and login form; Firebase handles password choice on its hosted action page. A consumed reset link proves email ownership (the Auth emulator marks it verified); sending the request never signs in or bypasses normal app checks.
- **App start and Verify Email (#30/#31/#74/#87/#99):** `AppStartViewModel` routes signed-out users to Welcome, retained unverified sessions to Verify Email (overriding restored auth navigation on cold start), and verified sessions through the profile check (Figma "App start · loading"; a failed read shows "App start · couldn't load profile" with Retry) to the app or the profile step; account-type routing is under "Associations". Verified login calls `refresh()` instead of bypassing the profile check, and verification success uses the same check. Saving the profile step calls `onProfileCreated()`, which opens the app without reading the profile again. `AuthRepository` reloads the account and forces an ID-token refresh before reporting verification; browser return refreshes verification and Continue retries manually. Resend deadlines (45 s after delivery, 3 min after throttling) are kept per UID and per SHA-256 digest of the trimmed, lowercased address (#225; only timestamps are stored), survive sign-out so re-login can't bypass the cooldown, and clear on verification; re-entry never automatically repeats a successful delivery. Verify Email uses two columns in wide, short windows. Saved signed-out forms survive recreation. Google is wired on Welcome and Log in (#107), and Welcome's association sign-up since #125. Log in accepts any email domain so associations can sign in (#208); its helper line says students use `@epfl.ch` and associations their own email.
- **Profile created at the first verified entry**, not at sign-up: the rules require `email_verified`, so a write right after sign-up is denied. Create it exactly once, on Verify Email "Continue" or when app-start routing finds a verified user without a profile; sign-up only saves the Auth display name.
- **Profile model (#34):** `UserProfile.isAssociationVerified` is `false` unless it is the boolean `true`, like the rules, so a typo by the admin can't make the profile unreadable; the client never writes it. Profile writes run in a **Firestore transaction** ("create once", "update only if it exists") that fails offline (`NetworkError`) instead of queuing, so the profile step can show Retry. Section and year are codes from fixed lists (`model/user/ProfileOptions.kt`). No profile photo or username yet (#34).
- **Signed-out navigation (#74):** Welcome, Sign up and Log in keep a small saved back stack in `AuthFlow`, so Back returns to the screen the user came from; opening a screen already in the stack goes back to it. Verify Email, the profile step and the app clear it. Back on the profile step (arrow or system) signs out to Welcome through `AppStartViewModel.logOut()`, which cancels a profile read in flight; Verify Email's Back and "Change address" go through `VerifyEmailViewModel.leave()` (see "Unverified accounts"). The profile step is reset each time it opens, so a step left before never comes back half-done. Every sign-out resets the retained auth state (see Traps).
- **Logout and the offline cache (#109, #156):** Profile's Log out asks for confirmation ([Figma, #108](https://www.figma.com/design/7Gt7tmy1ikpNyNBh1P6QdY/App-Mockup?node-id=673-118)), then clears Firestore persistence **before** `AuthRepository.logOut()`; a failed clear keeps the user signed in behind blocking Retry (team decision, [#177 review](https://github.com/swent-polysocial/PolySocial/pull/177#issuecomment-6168926664)). `AppShell` then removes active and saved tab stacks, and `AuthFlow` resets Welcome's Google state, login, sign-up, verification and profile-step state before Welcome. `FirestoreSession` owns the replaceable database and repositories resolve it per operation; cleanup serializes callers, runs termination and persistence removal with a 10-second timeout despite caller cancellation (then propagates it), and access fails through typed repository errors until it succeeds. Offline persistence stays enabled between logouts.
- **Session isolation ([#198](https://github.com/swent-polysocial/PolySocial/issues/198)):** `PolySocialApp.onCreate` starts the singleton `FirestoreSessionGuard` (`model/firebase`) once, with an app-wide `SupervisorJob` scope on `Dispatchers.Main.immediate`, so a UID change blocks the cache inside Firebase's auth callback, before the clear starts. It stores the last signed-in UID (SharedPreferences `session_guard`, key `uid`); a different UID (none → someone, A → B) runs `SessionCache.clear()`, then stores the new UID; the same UID across restarts clears nothing, and logout keeps its own clear. App start awaits `ensureSession(uid)` before its profile read, and its Retry runs the guard again; while a clear is pending or failed, `FirestoreSession.database` throws and each repository returns its typed error. An unexpected failure blocks the cache unless it is known to be empty, and observation goes on. An install from before the guard clears a signed-in student's cache once.
- **Privacy notice (#103):** Profile → Privacy & data is a read-only summary and a dated full notice, bundled so they work offline (the app shell supplies the destination to `ProfileRoute`; without it the entry is hidden). Export and attendance-based matching show "not available yet"; the switch stays Off and writes no consent. The collection/access text describes this build: update it when a feature changes what is collected (#121's and #123's when attendance or reminders are enabled). `privacy_contact_email` stays empty until supplied (see Open questions); Hilt provides the address and contact service to each entry's ViewModel, which opens a user-controlled email draft when configured and otherwise explains what is missing.

### Account deletion

- **Policy ([#201](https://github.com/swent-polysocial/PolySocial/issues/201), agreed 2026-10-28; built by #205–#207):** self-service for a signed-in **student** (not `accountType == "association"`), unverified accounts included. **Associations stay admin-assisted:** the flow refuses them (`NotAllowed`) and points to the privacy contact (see Open questions). The deletion/failure matrix is in the Architecture Diagram, section 7.
- **Events are kept.** `createdBy`, `organizerIds` and `allowedUids` keep the deleted UID (an opaque identifier) and nothing on the event is written, so other students' registrations stay valid. Co-organizers keep managing it; a sole organizer's event can no longer be edited or cancelled. A missing public profile can be a deleted account, an association or a student saved before #229 who hasn't opened the app since ([#291](https://github.com/swent-polysocial/PolySocial/issues/291)), so it must not read "Deleted user" on its own.
- **`deleteAccount`** (callable, Functions v2 `onCall`, Node 22; README "Cloud Functions"): region `europe-west6` in one constant shared with the client (Firestore is in `eur3`, a mismatch accepted on 2026-11-05: this rarely used call only pays a few milliseconds, and moving it changes both the function and the app). It requires `request.auth`, rejects an ID token whose `auth_time` is over 5 minutes old (`failed-precondition`, "recent-login-required") and associations (`failed-precondition`, "association", checked in the same transaction as the profile deletion so a profile written in between can't skip it). It deletes `users/{uid}` and `publicProfiles/{uid}` and writes the `deletedAccounts/{uid}` marker in one transaction, then the student's registrations (#275, after the marker, see "Registrations"), then removes sender account links from all messages and group memberships and their markers, then deletes the Auth user (Admin SDK). Every step is idempotent, so Retry finishes a partial deletion; it returns `{ deleted: true }` only after all. Later data (reminder metadata, photos) adds its cleanup here in its own issue. The Admin SDK bypasses rules. The pure `deleteAccountHandler` takes Firestore, Auth, the clock and the logger as arguments (unit tests use fakes); a failed step logs only its name and error code (no uid, message or stack).
- **No Functions SDK (#269):** `firebase-functions` is not a dependency: it pulled in `firebase-iid`, `firebase-installations` and `play-services-cloud-messaging`, which registered an Installation ID and an FCM token on every call and added the c2dm `RECEIVE` and `WAKE_LOCK` permissions. `FirebaseAccountDeletionRepository` (`model/account`) calls the callable over plain HTTPS (`POST {"data":{}}` with the ID token as a bearer token, `HttpURLConnection` on the IO dispatcher, explicit region and timeouts; the callable protocol's answers are mapped in `parseDeleteAccountResponse`'s KDoc). A new callable should follow it rather than bring the SDK back. Its tests use a local HTTP server; an emulator test waits until CI starts the Functions emulator.
- **Client timing:** before calling, the client waits for Firestore's pending writes and doesn't call if they can't be sent: an ID token stays valid up to an hour after the Auth user is deleted, so a write sent after the deletion could recreate an orphaned profile. Waiting and fetching the token share one 80 s bound; the request has its own 10 s connect and 60 s read timeouts, and a lost answer is covered by Retry. The cached token is refreshed only once expired; if a refresh runs, only `ERROR_USER_NOT_FOUND` means already deleted (`Deleted`), a disabled or revoked user is `NotSignedIn`. Firebase then signs the user out locally, so the flow captures the UID before starting.
- **Delete account (#207):** Privacy & data → Delete account opens a bottom sheet matching the Figma "Delete account" frames (section 08). Confirm → refuse offline (`NetworkMonitor.isOnline()`, never queued) → re-authenticate (password, or Google through #106's flow; `Cancelled` changes nothing, a Google failure reported as a cancellation is `UnexpectedError` (#319), `RecentLoginRequired` returns to this step) → call the function → on `Deleted`: clear the cache, `VerificationStore.clear(uid)`, log out and leave through logout's own reset (`AppShell.leaveApp`), and Welcome says "Account deleted". Retry after a failed call skips re-authentication; a failed cache clear uses logout's blocking Retry; duplicate taps are ignored. The client doesn't read the account type, so an association learns it can't delete itself (`NotAllowed`, with the privacy contact) only after re-authenticating. A lost session (`NotSignedIn`) runs the same cleanup and opens Welcome without saying the account was deleted. Figma's outlined "Continue with Google" is the shared `GoogleSignInButton`.
  - **Cancel after a lost answer** (decided 2026-10-29, [#270](https://github.com/swent-polysocial/PolySocial/pull/270)): Cancel on "Couldn't delete your account" stays as in Figma, even if the server finished and only its answer was lost; reopening Delete account (re-authentication answers `NotSignedIn`, then the cleanup) or #198's guard at the next start recovers.
- **Unverified accounts ([#149](https://github.com/swent-polysocial/PolySocial/issues/149), #225):** Verify Email's Back and "Change address" delete the account through `deleteAccount` before signing out: refused offline, no re-authentication step. The account is reloaded right before: **a verified one is never deleted**, only signed out with both its deadlines cleared, and one no longer found (`NotSignedIn`) finishes like `Deleted`. Offline, `NetworkError`/`UnexpectedError` and a failed reload keep the user on Verify Email with Retry and **Log out anyway** (signs out without deleting), so the screen keeps a way out while `deleteAccount` is down. `RecentLoginRequired` (signed up over 5 minutes ago), `NotAllowed` and `NotSignedIn` only sign out and keep the cooldown, so the address stays reserved until the 7-day cleanup. After `Deleted` the app clears the UID's `verification_timing` keys, signs out and opens Welcome (Back) or Sign up with the address prefilled (Change address). The per-address cooldown outlives the account, so signing up again with the same address keeps it; only the UID's own timing says whether a link was already sent.
- **7-day cleanup ([#226](https://github.com/swent-polysocial/PolySocial/issues/226)):** the scheduled `deleteUnverifiedAccounts` (daily at 03:00 `Europe/Zurich`, `deleteAccount`'s region constant; how it runs and fails is in the README's "Cloud Functions" and the handler's KDoc) deletes the Auth accounts whose email is still unverified **more than 7 days** after their creation, with any `users/{uid}` stored for them. The period is the one constant `UNVERIFIED_ACCOUNT_RETENTION_DAYS`, whose KDoc names the two texts that state it too (the README and the privacy notice). "Unverified" is the email, not an association's review. **Nothing else is cleaned and no `deletedAccounts/{uid}` marker is written:** every rule requires a verified email, so a never-verified account has written nothing and its token is refused before and after. So **a verified account must never become unverified again** (an email change, say) without first being kept out of this cleanup: it would lose its Auth user and keep its data. A failed run isn't retried; the next day's run continues.

### Profiles

- **Profiles are split (#229).** `users/{uid}` is owner-only. `publicProfiles/{uid}` holds `displayName`, `section`, `year` and `interests`, never the email, written in the **same transaction** as `users/{uid}`; students read it **by UID only, never as a list**, so no student directory is exposed (several are read in parallel); only its owner writes it; associations read none. The rules accept the copy only if it equals `users/{uid}` as it is after the write (`getAfter`). Once a copy exists, a `users/{uid}` update that changes those fields must write the same values to it (`keepsPublicProfile`, #229 review); a profile without one (saved before #229, or an association's) is exempt. Public or private visibility of further fields (Instagram-style) comes later.
- **Profile codes are repeated in the rules:** `SECTIONS`, `YEARS` and `INTERESTS` (`model/user/ProfileOptions.kt`) are copied in the rules (`interestCodes` for interests) and a rules test keeps them equal, so adding a code means updating both. **Interests (#230)** are stored as codes (labels only in `ui/common` and `strings.xml`); the rules check that each is known and appears once and compare the two lists with `==`, so the app writes both in `INTERESTS` order (`orderedInterests()`); an association's profile holds an empty list; readers drop codes no longer in the list. The profile step saves once, on Finish of its second screen.
- **Missing public copies (#291):** a profile saved before #229 gets its copy at the next app start: when `AppStartViewModel` opens the students' app, it starts `UserProfileRepository.ensurePublicProfile(uid)` in its own coroutine and doesn't wait for it. One transaction reads `users/{uid}`, then (for a student only, as the rules deny associations any `publicProfiles` read) `publicProfiles/{uid}`, and creates a missing copy from the stored profile; it never overwrites one or writes `users/{uid}`, and runs at every start. A failure opens the app anyway and is retried at the next start; new routing and `logOut()` stop waiting for it. No rules change. Until a student opens the app again, their public profile can be missing, so #231/#233 must not treat a missing profile as a deleted account.
- **Deleted accounts stay deleted (#294):** `deleteAccount` writes an empty `deletedAccounts/{uid}` marker in its profile-deletion transaction, and the rules refuse to create `users/{uid}`, write `publicProfiles/{uid}` or register for an event (#275) under a marked UID, because the deleted user's ID token stays valid for up to an hour. The app can't read or write the marker. **Deploy order:** `deleteAccount`, then the rules, then the app (README). A client deleting its own `users/{uid}` directly (the app never does) leaves the public copy until `deleteAccount` runs; removing that owner-delete rule is a separate team question.

### Associations

- **Associations have no EPFL email** (SIC, Fréquence Banane… use their own domain, often from Google for nonprofits). They sign up with their own verified email and can access their own account and setup until a PolySocial admin sets `isAssociationVerified` to boolean `true` by hand in the Firebase console ([README · Verifying an association](README.md#verifying-an-association), #135; only project owners). The [manual review workflow](docs/Association-Review.md) (#210) has project owners check representation and duplicates in the Firebase console. Accounts that are declined stay pending and can edit their setup. Owners can reconsider edits manually. The current flow has no rejection notice or resubmission action. A future admin interface requires a server-checked reviewer role. Rules: `AGENTS.md` "Authentication" (an `@epfl.ch` association is still an association, #161).
- **Onboarding (#125):** Welcome reuses signup and verification, which take the account type (default student); associations accept a valid email on any domain and omit the personal name. The UID-scoped setup form saves the private association account **before** the public `associations/{uid}` (#126), rejects existing student accounts, recovers a create whose answer was lost (a retry updates the identity with the latest submitted values) and keeps its input across retries and saved-state restoration; failed writes keep the form. The setup screen uses initials and the amber review notice; its description stays review-focused (#257 review, see Open questions). Validation lives once in `model/association/AssociationValidation.kt` (`associationFormErrors`; repository constants own the limits; websites require HTTPS with a host and valid port), shared with Edit details. The app never writes the verification flag.
  - **Same-device intent marker:** before remote signup, the controller records a private local digest of the email (no raw email or password; it grants no permissions; checked disk commits run off-main and block signup on failure). An existing private profile is authoritative, and the server's profile type supersedes the marker. With no private profile, non-EPFL accounts resume association setup even after reinstall; only EPFL accounts need the marker to tell student and association setup apart. Change address prefers the current completed signup type over a retained marker, so a later student signup can't inherit association mode. Marker cleanup after durable association typing is housekeeping: a failed write reports `RetryNeeded` and retries on refresh without blocking entry.
  - **Empty `displayName` (#143, #256):** association setup writes `displayName = ""` and the name lives only in `associations/{uid}`: names go up to 60 characters but `displayName` stops at 50, and a copy would go stale after Edit details ([proposed on #256](https://github.com/swent-polysocial/PolySocial/pull/256#pullrequestreview-5696457857)). Nothing reads `displayName` for an association.
- **Routing (#127, #208, #258):** `AppStartViewModel` routes by account type, never email: a student gets `Main`; an association without its identity gets `AssociationSetup`; an unverified one gets `PendingAssociation` (`PendingAssociationApp`: Events with the review steps, Map closed until verified, Organization to edit its details and log out); a verified one gets `AssociationMain`. Approval or revocation takes effect at the next app start. **Fail closed (#208):** a session whose Auth email isn't exactly `@epfl.ch` (`isExactEpflEmail`, the rules' case-sensitive check, shared with Google sign-in) never gets `ProfileSetup` or `Main`: without a profile it resumes association setup unless its domain is `epfl.ch` in other letter case, and with a student profile it gets `StartDestination.Error`, which offers Retry and a Log out link (`ErrorState`'s optional `ErrorAction`, through `ui/profile/ActivityLogout`, shared with the pending app). Student Profile never queries associations. Organization reuses Profile's Privacy entry and logout (`LogoutDialog`, cache cleared first). Edit details (pending) saves with `updateAssociation` and keeps the form on failure. Unbuilt management entries show the "not available yet" Snackbar; no invented event/member/attendance counts, invitation badges or edit flow.

It holds exactly `name`, `type` (stored by enum name), `about`, an optional `website` and a server-set `createdAt`: no `uid`, email or verification field. Limits, the same in the rules and the form (UTF-16 units): name 1–60 and about 1–1000, neither blank; website at most 200, `https://` then no whitespace. Writes are transactions like the profile's (create once, update only if it exists, offline `NetworkError`), and the owner's `users/{uid}` must be saved as an association's **before** `createAssociation`, not in the same batch (the rules read it as it was). **Rules:** the owner reads and writes it, pending or verified; **students read it only once the owner is verified**, and a denied read is `NotFound`, so a pending association looks missing; other associations never read it; no list, no client delete. **Once verified, `name` and `type` are fixed** (the badge stays on the name the admin checked), so the verified Organization tab shows them read-only and a rename goes through the admin. The logo is shown as initials until Cloud Storage uploads exist.
- **Association names on events (#128):** the students' Events cards, the map preview and the event detail show an association event's name, from Figma's "(#128)" frames in section 03: a "Verified" pill and "· by <name>" on the cards, "by <name> [Verified]" on the detail, and the badge without the name ("Verified association" on the detail) while or when the name can't be read. ### Events

- **Anyone can create an event** and becomes its organizer; `Event.organizerIds` (always containing `createdBy`) controls who can manage it. Only a verified association publishes under its name: its events get `isAssociationEvent`, which shows a verified badge. An unverified association account can't create events or add members until it's verified (the rules deny its event creation, #47), and #127 routes it to its pending app (no "+"). A denied write reaches the app as `UnexpectedError`, so Create Event has no access-denied state.
  - **The creator is the only organizer for now.** `organizerIds` and the rules (#47) already allow several. **Co-organizers come in Sprint 5 (#280):** an organizer adds students picked among the event's registered attendees (organizers can already list them, so no student directory is exposed), at most 5 organizers, the creator can't be removed, and every organizer stays in `allowedUids`. Association co-organizers need new rules and wait for a team decision at Sprint 5 Planning (Architecture Diagram, decision 17; #228).
  - **"Cancel event" deletes the event**; there is no "cancelled" status.
- **Event fields** (`model/event`, #45): `title` is required and at most 80 characters; `description` may be blank and is at most 5000 (in line with Meetup and Eventbrite); the rules use the same limits. `endTime` is optional and must be after `startTime`; the form treats an earlier end time as the next day (22:00 → 02:00, shown as "+1 day"). `capacity` is optional and at least 2. `category` is one of Study, Sports, Culture, Party or Other (the Figma chips); an unknown stored category reads as `OTHER`, never a crash. `location` is plain lat/lng (`Coordinates`), not a map SDK type. `locationName` is the picked place's name (at most 100 characters, rules too; the form shortens a longer one without splitting an emoji), stored since #112; older events read it as blank. No address is stored, since the Figma detail shows only the name. Validation is the pure `validateNewEvent`, which compares the start time with the current minute.
- **Creating an event** (`EventRepository.createEvent`): `withCreator` makes the signed-in user the creator, the only organizer and the only allowed reader, and sets `isAssociationEvent` from the creator's profile; values the form sends for these fields are ignored. Checks run in a fixed order (invalid, not signed in, offline), and offline (`NetworkMonitor.isOnline()`, `model/network`, a one-off check that needs working internet) returns `NetworkError` without starting a write. It writes in a transaction, which only runs against the server. A failed profile read returns `NetworkError` or `UnexpectedError` without writing, so a verified association never publishes without its badge; a user without a profile gets no badge. The rules allow `isAssociationEvent == true` only when the creator's `users/{uid}` is a verified association.
- **Editing and deleting** (`updateEvent(event)`, `deleteEvent(id)`, #130): any organizer, not only the creator. Same checks as `createEvent` (an update is validated first, except a start in the past), then **one transaction** reads the stored event, checks the user is in its `organizerIds` and writes. **Started events stay editable:** `validateEventUpdate` refuses a past start only when it differs from the stored start, so a typo can be fixed during the event but no event can be moved into the past ([#213's review](https://github.com/swent-polysocial/PolySocial/pull/213)). The write is a Firestore `update`, not `set`, so fields `Event` doesn't hold survive an edit, and `withOwnershipOf` keeps the stored `createdBy`, `organizerIds`, `allowedUids` and `isAssociationEvent` whatever the form sends (changing organizers or readers needs its own issue). Results: `NotFound` for a missing, malformed or unreadable event (a **denied read is `NotFound`**: reading a missing event is denied by #52's rule, and a private event must look missing), also when deleting an event that no longer exists; `NotOrganizer` for a non-organizer, nobody signed in, or a **write** the rules deny. **Deleting removes only `events/{id}`:** Firestore keeps subcollections, and once the event is gone no client can read them (see Open questions, #275). Reminders are local, so the reminder worker checks that the event still exists.
- **Upcoming public events** (`getUpcomingPublicEvents(windowDays = 14)`, #49): a live, conflated `Flow<PublicEventsResult>` from a snapshot listener (cached events while offline), so new events appear by themselves; the final `Error` is never dropped. "Upcoming" is the pure `isUpcomingPublicEvent`: public and starting from now (included) to now + `windowDays` (excluded), fixed when collection starts; events already started are not shown. Reading is the hand-written `eventFromFirestore` (see Traps): a document missing a required field is skipped.
- **Event detail (#112):** `EventRepository.getEvent(id)` is a live, conflated `Flow<EventResult>` with metadata changes: `Found(event, fromCache)`; `NotFound` for a missing, deleted, malformed or **denied** event (a denied private event looks missing; the flow then ends); `NotCached` when Firestore considers itself offline and never read it. While online, the detail waits at most 10 s from the start of each read (`SERVER_ANSWER_TIMEOUT_MILLIS`, #194), then shows the offline "not saved" state with Retry, which starts a new read; a late answer still shows the event. Offline states also need `NetworkMonitor` to say offline (see Traps on `fromCache`). Times show in the device zone with an end-day offset ("+1 day"). The detail hides the app bar and the bottom bar and draws edge to edge; taps during a navigation transition are ignored, so a double Back can't empty the stack. It follows Figma section 03's reduced frames: no Share, ⋯ or audience chip until their issues, "I'm going" (#122), its "Remind me" toggle (#123's second PR, below), the group card (#233) and association names (#128).
- **Create Event** (#44, #46, #110; Figma section 04) opens from the "+" on the Events and Map tabs as a route in that tab's graph, full screen (no app bar or bottom bar), so Close and Back return to that tab. Fields: title, description, category, date with a start time and an **optional end time**, location (search or map pin), optional capacity, private or public. The form logic is pure Kotlin (`CreateEventForm`): an error shows under its field once that field changes, all errors show when Create is tapped with problems left, and the button then stays disabled until they're fixed. After creating, an **"Event created" confirmation** offers *View event* and *Back to map* (team decision, 2026-10-06): "View event" replaces it with the new event's detail (#211), so Back skips the confirmation; "Back to map" pops it before switching to the Map tab. Offline, it shows the offline error with *Try again*, keeping the form. On the map, `MapScreen` places the "+" itself, with the location button 12 dp above it, and hides it while an event card is open.
- **Organizer row (#134):** the top of the Create Event and Edit event form shows Figma's "Create event · association" row (initials, "Organized by <name>", Verified badge) to a verified association, read once at opening from its profile and then its `associations/{uid}`; everyone else, and any failed read, gets "Organized by you", and the form never waits for it. While loading, the row holds that text's space without drawing it. Initials follow Figma ("AGEPoly" → "AG"; several words: first and last word). The student row still lacks the Figma student frame's avatar.

On the detail, an organizer (signed-in UID in `organizerIds`) sees Edit, "Organized by you" and Cancel event; other students see none of them. Cancel event opens a "Cancel this event?" sheet that can't be dismissed while deleting and stays with the reason and Try again when offline or refused; once deleted, the detail pops back without flashing "not found" and the app shell shows "Event cancelled".

### Registrations, groups and chat

- **Registrations (#121):** `events/{eventId}/attendees/{uid}` with only `uid` (the student's UID again) and `registeredAt` (server time). A student's own registrations are read with the **collection-group query** `attendees where uid == <their UID>` (no mirror under `users/{uid}`), which needs the deployed field index. `register` reads the event and the registration in one transaction and writes only if missing (idempotent, keeps the first `registeredAt`); a missing, deleted or unreadable event is `NotFound`. `cancel` deletes in a transaction (deleting a missing one succeeds). Both fail offline with `NetworkError` instead of queuing; `observeMyRegistrations` works from the cache. **Rules:** a student creates only their own document, for an event they can read **that hasn't ended** (its `endTime`, or its `startTime` without one; a refused write is `UnexpectedError`, so screens don't offer it for past events), and deletes it at any time, even once the event has ended, is deleted or is unreadable; the event's organizers get and list its attendees; a student lists only their own; nobody updates one; associations never register. **Organizers see who registered**, not only a count: Firestore's `count()` also needs `list` (see Open questions on a counter). **Deleted with their event and account (#275):** `deleteEvent` still deletes only `events/{id}` on the client; the trigger `deleteEventRegistrations` (`onDocumentDeleted("events/{eventId}")`, **region `europe-west1`**, since Eventarc delivers `eur3`'s Firestore events only to `europe-west1`/`europe-west4`, deployed with retries) then deletes `events/{id}/attendees/*` with the Admin SDK, 500 per transaction, querying again until none is left; each transaction first reads the event and stops if it exists again, since the demo seed script writes its events back under the same IDs with new registrations (#328 review). A client batch was rejected: nobody can list the attendees once the event is gone, so a registration written between the client's list and its delete would stay forever. `deleteAccount` deletes the student's registrations (the collection-group query on `uid`) after the `deletedAccounts/{uid}` marker and before the Auth user, and the rules refuse a registration under a marked UID, so the deleted user's still-valid token can't add one afterwards. **Not built yet:** the capacity check (Open questions).
- **"I'm going" (#122):** the detail's action bar has "I'm going" next to Find a group (Figma "Event detail", `133:574`), then "✓ Going" with "You're going. Cancel registration" (`558:2`); organizers get only Find a group (`892:118`); a student in a group gets "✓ Going" across the bar, since the group card replaces Find a group (`1118:238`); an ended event drops "I'm going" and Find a group, though a going student keeps the note and its Cancel link (the privacy notice promises it stays available). `EventDetailViewModel` observes `observeMyRegistrations` alongside the event; a failed read still offers "I'm going", since registering twice changes nothing. A save disables both actions with a progress indicator, and a failure keeps the state with a Snackbar whose Retry saves again. Cancelling has no confirmation until #244 adds Figma's "in a group" sheet (`1132:323`); until then a student in a group doesn't see "Cancel registration" at all (it would leave them in the group without being registered), which #318 tracks. "Event full" (`558:60`) waits for the capacity decision.
- **Chosen events (#203, #320):** `ChosenEventsRepository` (`model/registration`) resolves the signed-in student's registrations to events with one `getEvent` listener per registered ID, so they have no 14-day window and one denied private event can't fail the others (rules aren't filters). It also lists the private events the student may read (`getReadablePrivateEvents`: `isPrivate == true` and `allowedUids` array-contains their UID, the shape the rules accept, with no order and no time window; needs the deployed `isPrivate` + `allowedUids` composite index), so an organizer, member or approved requester finds a private event without registering. Each event is listed once (the private query wins); every other registered ID ends up in `events`, `unavailableIds` (only the ID, like `NotFound`), `notCachedIds` or `pendingIds` (no answer yet: the caller times out, see Traps), as its KDoc details. The two reads are independent: `waiting` until both answered, `failed` if one failed (the other's events are still listed), `Error` only when both failed. Both read the student when collection starts, so a new account needs a new collection.
- **Groups (#228, built by #232):** `events/{eventId}/groups/{groupId}`, under the event like the registrations, with `capacity` (always **4**, a product decision, stored so it can change), `memberUids` (1 to `capacity`, the creator first), `createdBy` and server `createdAt`. Joining adds only the caller's UID to `memberUids` and leaving removes only theirs; the last member to leave deletes the group. The rules check `memberUids.size() <= capacity`, so the capacity needs no counter; the client's transaction stops two students taking the last place. **One group per student per event:** the marker `events/{eventId}/groupMembers/{uid}` (`groupId`) is written and deleted in the same transaction as `memberUids`, and the rules tie them with `getAfter` (an Android transaction can't query, so the marker is how it sees "already in a group"). A student who can read the event may join; Find a group requires "I'm going" (#244). Members may `get` their own group without the event (#295), so a student removed from a private event's `allowedUids` can still leave it. Associations never reach groups, messages or public profiles. Writes refuse offline (`NetworkError`).
  - **`GroupRepository` (`model/group`):** `observeGroups` (every group of the event, oldest first, **full ones included**: matching leaves them out), `observeMyGroup` (a query on `memberUids array-contains` the UID, not the marker), `createGroup`, `joinGroup` and `leaveGroup` returning `GroupWriteResult`; the results and the order of the join checks are in its KDoc. A write denied after its reads reruns (see Traps). `FakeGroupRepository` (sharedTest) has the same semantics. A student's groups across events would use a collection-group query on `memberUids` (rules only, no caller yet) with the `groups.memberUids` field override in `firestore.indexes.json`, which must be deployed.
- **Matching (#231)** is a deterministic heuristic in a pure Kotlin module, run **on the device**: `rankGroups` (`model/group`; scoring, tie-break and exclusions in its KDoc) takes its own `MatchProfile` / `MatchGroup` inputs and returns the open groups ranked, full groups left out, with the reasons to show (shared interests, members in the same section and year). A Cloud Function only if fairness or cheating becomes a problem.
- **Find a group (#233):** `tab.findGroupRoute` (`<tab>/event/{eventId}/groups`), one level below the detail, full screen, from #227's Figma section 11. `FindGroupViewModel` observes `observeGroups`, reads the members' and the student's public profiles once per change (`getPublicProfiles`) and ranks with `rankGroups`; a profile that can't be read leaves the member unnamed ("?") and scores nothing, so the groups still show. Join and Start a new group run one write at a time and are disabled offline. Only `GroupWriteResult.Success` leaves the screen (back on the detail, the app shell says "You joined the group." or "Group started."); every other result stays with its Snackbar.
- **Group chat UI (#238, Figma approved in #236):** the student roster opens chat for its group ID. The message listener stays active through member-list and cache metadata updates as long as the student remains in that group. Profile reads follow the member list separately. The timeout applies to the first load per attempt, and the offline banner follows the connection independently of messages. Losing membership clears the timeline and draft. Failed sends stay editable and use the original ID for an unchanged draft.
- **Group card (#233):** on the students' detail, `EventDetailViewModel` observes `observeMyGroup` once the event shows and reads the other members' public profiles each time the group changes (not when only `fromCache` does, unless the last read failed). The card ("Your group · 3 of 4") shows **instead of** the Find a group bar as soon as the group is known, names filling in as their reads answer; not in a group, or a group that can't be read, keeps Find a group. Tapping the card opens the student's group screen (#234). Associations never see Find a group: their managed events never observe groups, and their Map preview has none.
- **Group chat** (#237): `events/{eventId}/groups/{groupId}/messages/{id}` with exactly `senderId`, `text` (1–1000) and server `createdAt`; members read and send, each only their own messages, a deleted account (`deletedAccounts/{uid}`) can't send, nobody edits or deletes yet; rules per operation so rate limiting fits later. Membership comes from the group's `memberUids` alone, like the group's `get` rule (#295), so a member removed from a private event keeps the chat. Sending is **refused offline** with Try again, not queued. No message content is logged. A one-to-one chat is a two-member group (one model, one set of rules).
  - **`MessageRepository` (#237, `model/chat`):** `observeMessages(eventId, groupId): Flow<MessagesResult>` (the query `orderBy("createdAt")`, its order kept; `createdAt` read with `ServerTimestampBehavior.ESTIMATE` so a pending time isn't skipped; malformed messages skipped; `Loading`, `Success(…, fromCache)`, ending on `NetworkError`, or `UnexpectedError` for a non-member or nobody signed in; a member who leaves while listening gets `UnexpectedError` only at the chat's next change, see Traps) and `sendMessage(eventId, groupId, text, messageId = null): SendMessageResult { Sent, Invalid(MessageTextError), NetworkError, UnexpectedError }`. The text is trimmed, then `validateMessageText` (shared with the screen) refuses blank or over `MAX_MESSAGE_LENGTH` UTF-16 units; then the IDs, the user and `NetworkMonitor` are checked, and the message is written in a transaction tried once. For #238 the chat screen generates a UUID per draft, keeps it on Try again, and makes a new one when the trimmed text changes. If the ID already holds the same sender and trimmed text, the transaction returns `Sent`; a different sender or text returns `UnexpectedError` without changing it. `NetworkError` means the server couldn't confirm the send and nothing was queued. Omitting the ID generates a new one each time. `FakeMessageRepository` (sharedTest) follows the same retry behavior. The chat UI uses `observeMyGroup` to react when the student leaves, and the privacy notice describes the stored message fields and device cache.
- **Find my group:** positions in `events/{eventId}/groups/{groupId}/locations/{uid}`, written only during the event, readable by members only, deleted afterwards. No location history.
- **Group roster (#234):** observes membership on the student route and reads each member's public profile independently so one cache miss leaves a placeholder without hiding other cached profiles. A missing profile says “Profile unavailable” (#291). Leave follows validated connectivity even when the group does not emit. Confirmation targets the displayed group, and only a successful leave returns to the event.
- **QR codes (approved libraries):** CameraX + ML Kit barcode scanning reads codes (not added yet). Drawing one uses **ZXing `core`** (added by #339, pure Java; approved by Mohamed for the team on 2026-11-11, "use the industry standard"): `encodeQrCode` (`model/qr/QrCode.kt`) turns a payload into modules (error correction M) and the screen draws them, so never encode or draw a QR code another way.
- **QR payloads (built, #337):** `polysocial://checkin/{eventId}/{token}` and `polysocial://friend/{uid}`, read and written only through `parseQrPayload` and `friendQrPayload` (`model/qr/QrPayload.kt`), never a second reader or a hand-written payload string. The parser is strict (exact lowercase scheme and host, IDs of 1 to 128 `[A-Za-z0-9_-]` that aren't Firestore's reserved `__…__`, no query, fragment or trailing slash) and has one `Invalid` result, since every screen shows the same message.
- **Friends (#338, design only, not built):** one `friendships/{pairId}` document per pair of students, `pairId` = `{lowerUid}~{higherUid}`, with `uids` (sorted), `requestedBy`, `status` (`pending` → `accepted`), server `createdAt` and `acceptedAt`. Declining, cancelling and removing delete it, so two students never have more than one request (both directions share the ID; the second create is refused and the app offers Accept). Added by scanning `polysocial://friend/{uid}` (#337) and reading the public profile by UID; **no usernames** (open question). One listener on `uids array-contains <UID>`, split on the device into friends, incoming and sent; writes refused offline; requests shown in the app (no FCM). Rules: students only, only the two read or write; create by the sender with the fixed fields and a target that has a public profile; accept by the recipient only; a caller under a `deletedAccounts/{uid}` marker can't read, accept or delete, and accepting is refused if either student is marked. Every action runs in a transaction that compares the shown `status` and `createdAt` and returns `Gone` if they changed (so a stale Cancel can't remove a new friendship). `deleteAccount` deletes the UID's friendships. Details: Architecture Diagram 3.7.
- **My friend code (#339):** Profile's "My friend code" row opens `Tab.PROFILE.friendCodeRoute`, full screen like Privacy (Figma section 15, plus the "couldn't show" frame `1291:217`). `FriendCodeViewModel` encodes the signed-in UID at once, with no network, so it works offline, then reads the student's own profile for the name, section and year; a failed read keeps the code and the account's name. Students only: the Organization tab passes no `onOpenFriendCode`, an association's graph has no friend code destination, and an association's profile gets "Can't show your code". **Drawing a QR code:** pure `Color.Black` on `Color.White`, never theme colors (a theme change must not make it unscannable), with the 4-module quiet zone inside the code's own square, and the square shrinks below Figma's 205 dp when the visible width or height is smaller, so the whole code always fits on screen; tests decode the image exactly as drawn, with no added margin (#384 review). "Scan a friend's code" comes with the scanning task (#359). The row and title row are shared with Privacy (`PrivacyActionRow`, `PrivacyHeader`).

## Traps

### Firestore and Security Rules

- **Security Rules are not filters.** A query that could return a document the user can't read fails entirely. Public events need `where isPrivate == false`. Private events need `where isPrivate == true` and `array-contains` the signed-in UID on `allowedUids`. Association event queries need `createdBy == auth.uid` and `isAssociationEvent == true`; the association verification comes from its protected `users/{uid}` document, never client-supplied token claims. An association (whatever its email domain) cannot run the student map's unrestricted public query.
- **Private rules use `allowedUids.hasAny([auth.uid])`.** This list-only operation denies malformed map/string allowlists and supports `array-contains` queries. Adding a separate `allowedUids is list` check makes even the valid query fail in the emulator's rules evaluation.
- **A missing field makes a rule fail, not compare false.** `get(...).data.accountType == 'association'` errors, and so denies, when a student's profile has no `accountType`. Read optional fields with `data.get('field', default)` (#47).
- **Rules deny by default since #35:** a new collection is unreachable, even in the emulator, until its own `match` block is added. Never bring back a broad `match /{document=**}`: Firestore allows access if any matching rule allows it, so it would reopen everyone's `users/{uid}`.
- **Composite indexes aren't enforced by the emulator.** A query missing from `firebase/firestore/firestore.indexes.json` (for example `isPrivate == false` with a `startTime` range, #49) passes the emulator tests and only fails on the real backend, also when the index is versioned but not deployed. Add the index by hand and deploy it (README).
- **Don't let Firestore map `Event` automatically** (`set(event)`, `toObject`). It stores the Kotlin property `isPrivate` as `private` (and `isAssociationEvent` as `associationEvent`), so queries and rules on `isPrivate` never match, and reading needs a no-argument constructor. Convert to and from a map by hand (writing: `Event.toFirestoreMap()`).
- **Firestore queues writes while offline** instead of failing them, so a screen that waits for a write would spin forever. Any repository whose write the UI waits for checks `NetworkMonitor` first and returns `NetworkError` (#45), and writes in a transaction, which only runs against the server.
- **`FirebaseFirestore.disableNetwork()` does not make transactions fail.** They still reach the server and succeed, so it can't test the offline `NetworkError` path of `FirestoreUserProfileRepository`. The emulator tests use airplane mode instead (`cmd connectivity airplane-mode enable`), which makes create and update return `NetworkError` after about 8 s (#119).
- **A transaction that lost a race fails with `PERMISSION_DENIED`, and Firestore doesn't retry it.** The emulator checks the rules on a transaction's writes against the documents as they are at commit, before any conflict check, so a write computed from a group another student just changed is denied instead of retried (#232). `FirestoreGroupRepository` reruns a transaction denied after its reads (up to 3 times), so the student who lost the last place gets `Full`. Any transaction whose rules compare the write with the stored state needs the same.
- **`fromCache` alone doesn't mean offline.** With metadata changes included, Firestore's first snapshot of cached data comes from the cache even online, until the server answers. Show an offline banner only when `NetworkMonitor.isOnline()` is also false (review of [#145](https://github.com/swent-polysocial/PolySocial/pull/145)).
- **Firestore can stay silent about a missing document.** While it thinks it is online, it withholds the cached "missing document" snapshot of a never-read document until its own offline detection (about 10 s) or a stream failure, and it may emit nothing at all if the connection dies silently. A screen waiting for a server answer needs its own timeout from the start of the read (#194).
- **A listener isn't revoked when a document its rules `get()` changes,** only when its own results change. A student who leaves a group keeps a silent chat listener; the next message ends it with `PERMISSION_DENIED`, without delivering that message (seen on the emulator, #237). Watch the document that grants access (`observeMyGroup`) to react at once.
- After the email is verified, **force an ID-token refresh** (`getIdToken(true)`), or the rules still see `email_verified == false`.

### Auth, sessions and navigation state

- **Auth completion effects leave with the screen.** System Back must keep sign-up and login in composition during submission and successful routing; otherwise the account can be created or signed in without reaching its destination. In-screen login Back/Create account are locked too; failures unlock navigation. Regression tests use deferred fake repositories ([#87](https://github.com/swent-polysocial/PolySocial/pull/87)). The profile step does the same while saving (#74).
- **Sign-out must reset what outlives the screen.** `AuthFlow`'s ViewModels belong to the activity. When the start destination moves to `Login` (a sign-out, from anywhere), `AuthFlow` resets the sign-up and log-in forms (a kept `SignedUp` or `LoggedIn` status redirects at once), verification (including pending checks and the previous email, while keeping per-account resend cooldowns), and the profile step (it holds the account's name and email). The same shared reset runs on Profile logout and Verify Email Back/change address. Anything else that caches the signed-in account must be reset there too. A recreation replays the current destination, so `AuthFlow` remembers the last one it applied to tell the two apart (#74).
- **The signed-in apps' ViewModels can outlive the session.** `AuthFlow` isn't in a NavHost, so a `hiltViewModel()` it (or the pending association app) creates outside a nav entry belongs to the activity. The pending app therefore resets its logout state and forgets the association on Log out, and reads it again for each session; logging out then in as another account without restarting must keep working (`PendingAssociationFlowTest`, [#127](https://github.com/swent-polysocial/PolySocial/issues/127)).
- **Association names (#128) recheck the account only when a collector starts and on each new name.** `CachedAssociationNames` is a singleton, so a screen that stays alive across an account switch would keep the previous account's names. Today the account only changes through logout, which clears every tab's back stack; keep it that way, or combine `names` with an auth-state flow ([#252](https://github.com/swent-polysocial/PolySocial/pull/252#issuecomment-6494137979)).
- **`onProfileCreated()` opens the students' app.** Fine while the profile step only creates students (association setup, #125, has its own destinations); an association profile created there would need `PendingAssociation` ([#127](https://github.com/swent-polysocial/PolySocial/issues/127)).
- **Google picker context (#107):** the ViewModel coroutine can hold the initiating Activity until the repository operation returns or is cancelled, including across recreation. Never store an Activity in UI state or repository fields. Offline pending-attempt restoration tests do not prove real Credential Manager rotation behavior; that still needs device validation ([#168](https://github.com/swent-polysocial/PolySocial/pull/168)).
- **Google failures arrive as a cancellation (#319).** Credential Manager throws `GetCredentialCancellationException` both when the user closes Google's sheet (`[16] Cancelled by user.`, or androidx's `activity is cancelled by the user.`) and when Google's sheet fails (`[16] Account reauth failed.`, reported elsewhere with an unregistered SHA-1, an OAuth consent screen set to Internal, or no network). The status code is the same, so `isUserDismissal()` (`model/auth/GoogleSignIn.kt`) checks Google's English wording: an empty message or one that says "cancel" is a dismissal, anything else a failure. Sign-in and Delete account's re-authentication both use it; a new Google flow must too. If Google rewords its dismissal, a real cancel shows the error screen (recoverable, never silent).

### Compose and UI

- **Draw a shared composable once, above a `when`.** The same composable called in two branches is two different nodes, so switching branches recreates it: a text field loses its focus and cursor mid-typing ([#178](https://github.com/swent-polysocial/PolySocial/pull/178)).
- **`hiltViewModel()` outside the `NavHost` returns the Activity's ViewModel,** which logout never clears, so it outlives the account (the association header in the app bar showed the previous account's name, #326 review). Give such a composable a back stack entry as its `LocalViewModelStoreOwner`, for example the start destination's graph, which logout pops.
- **A locked `ModalBottomSheet` still calls `onDismissRequest`** for Back (`confirmValueChange` only covers the scrim and swipes). Use `ConfirmationSheet` (`ui/common`), which ignores that call while `locked` ([#296](https://github.com/swent-polysocial/PolySocial/issues/296)).
- **Feedback effects must key both their text and their owner's callback** (#103): replacing a ViewModel that shows the same message otherwise dismisses the previous owner's message.
- **A ViewModel that starts work in `init` binds `viewModelScope` at construction.** A test that creates it as a field, before `MainDispatcherRule` sets the test dispatcher, ties every later coroutine to the real Main dispatcher, so nothing the test advances runs. Create such ViewModels lazily or inside the test (#134).
- **Matching Figma in Compose** (found on the profile step, #34):
  - Lay a screen out with a `Column` and Figma's gaps as `Spacer`s, not at absolute Figma positions; the few dp of pixel rounding this adds down the screen are accepted (review of [#95](https://github.com/swent-polysocial/PolySocial/pull/95)).
  - Give texts `TextMotion.Animated`: Android otherwise rounds each glyph to a whole pixel, so long texts come out about 1 dp narrower than Figma.
  - Multi-line texts with a line height need `LineHeightStyle(Center, Trim.None)`; Compose trims the first and last line by default, Figma doesn't.
  - Material's `DropdownMenu` keeps a 48 dp margin from the window edge and opens *above* a field near the bottom of an 800 dp screen; use a custom `Popup` when Figma shows it below.
  - Check on a device, not Robolectric (its text metrics differ): render the state, export the Figma frame at the device scale, and compare element by element.
  - Robolectric's default (legacy) graphics never draw an ellipsis and give every text line a fake height. A test of shortened text, exact heights or large font sizes needs `@GraphicsMode(GraphicsMode.Mode.NATIVE)`, ideally at the Figma frame's size (`@Config(qualifiers = "w360dp-h800dp")`) (#134).

### Tests

- **A tab screen that uses `hiltViewModel()` breaks tests that render `AppShell` or `AuthFlow`** in a plain `ComponentActivity` (no Hilt there). Both take the screen as a parameter with the real one as default (`AppShell(eventsContent = …)`, `AuthFlow(signedInContent = …)`), and those tests pass a placeholder; a new real tab adds its own parameter the same way (#105).
- **The real Mapbox map can't run under Robolectric** (`UnsatisfiedLinkError` on `Map.getSupportedRenderBackend`), and a developer's or CI's `local.properties` has a token. A JVM test that opens a Map tab must pass a fake `renderer` (or blank the token as `AppShellDefaultScreensTest` does); a full-app test through `MainActivity` must not open the Map tab (#133).
- **A Hilt test that uninstalls `FirebaseModule` must also replace every module that needs Firestore** and that a `@HiltViewModel` injects, even one its screens never open: Hilt checks every ViewModel's dependencies when it builds the component. So `LogoutInjectionTest`, `DeleteAccountInjectionTest` and `M1EndToEndTest` bind fakes for `GroupModule`, `PublicProfileModule` (#233) and `RegistrationModule` (#131). #238 adds `MessageModule` to that list. Bind the chat fake with `@BindValue` in each affected UI test so other tests keep the real module.
- **Uninstalling `AuthModule` in a Hilt test also drops the session guard's bindings.** `PolySocialApp`'s injector is part of every Hilt test component, even under `HiltTestApplication`, so such a test must `@BindValue` a `SessionGuard`, an `AuthSessionSource` and a `SessionOwnerStore` (fakes in `app/src/sharedTest`), or Hilt fails to compile. Under `HiltTestApplication` nothing starts the guard; a test that needs it starts it itself (#198).
- **A new repository method called at app start breaks strict MockK mocks in device tests.** `GoogleSignInScreenTest`, `SignUpScreenTest` and `VerifyEmailScreenTest` use `mockk<UserProfileRepository>()` with only `getProfile` stubbed, so an unstubbed call throws `MockKException` inside a launched coroutine and crashes the test; only CI's instrumented shards show it (#291's `ensurePublicProfile`). Search `app/src/androidTest` for `mockk<` of the interface you change, stub the new method, and run the full `connectedCheck` before pushing.
- **An endless loop in `viewModelScope` turns a failed `runTest` assertion into a hang.** `viewModelScope` isn't a child of the `TestScope`, so a loop that never ends there (the Verify Email resend countdown on a fixed `VerificationClock`, or a "Live now" ticker) keeps `runTest`'s cleanup advancing virtual time forever once an assertion skips the ViewModel's disposal, and CI only reports the job's timeout. Dispose such ViewModels in a `finally`, like `VerifyEmailViewModelTest`'s `runVerifyTest` (#292). A loop launched in the test's own scope is cancelled with the test and is fine.
- **Verification UI tests must wait for enabled Continue.** Initial email sending and lifecycle verification checks disable it; Compose idleness alone does not guarantee startup work has finished, and a click on a disabled button is ignored. Use observable UI conditions instead of sleeps; for callback/navigation checks, semantic click actions target Continue even when transient UI overlaps it ([#99](https://github.com/swent-polysocial/PolySocial/pull/99)).
- **The soft keyboard moves the screen after Compose is idle (#314).** It is another process (the input method, such as Gboard) that opens late: when typing returns it may not have started, or still be sliding in, and Compose's idling doesn't wait for it. On a screen with `imePadding()` a button scrolled into view then leaves the screen, so the tap lands where it was (sign-up never reached Verify Email) or a later display check fails. Device tests call `closeKeyboard()` (`app/src/androidTest`, waits until it's gone) after typing, before tapping or checking what's below the fields; it covers the activity's window only, not a dialog or a bottom sheet.
- **Logout navigation tests must retain the controller.** A fresh shell hides missed teardown. Assert the active stack is empty, then try restoring a previously saved tab on the same controller; `clearBackStack()` returning `false` after the active stack is empty does not prove there was no saved state ([#177](https://github.com/swent-polysocial/PolySocial/pull/177)).
- **Material 3's date picker opens on the device's current month**, whatever the injected `Clock` says. A test that taps a day in the calendar depends on the real date; switch the dialog to text input mode and type the date instead (#136).
- **A single-document `get(Source.CACHE)` never completed under Robolectric** (#198); `SessionGuardCacheTest` and `FirestoreCacheResetTest` read the cache with a collection query instead.
- **Compose coverage:** JaCoCo can count unreachable change-mask branches when a callback captures an unstable ViewModel parameter. Do not pad tests to hit compiler paths or exclude application code; use meaningful recovery/lifecycle tests, and for shared actions consolidate callback ownership outside Compose ([#168](https://github.com/swent-polysocial/PolySocial/pull/168)).

### Build, CI and emulators

- **Local Java version:** the host default Java 27 causes JaCoCo test instrumentation errors (`Unsupported class file major version 71`). Run Gradle with the installed Java 21 via `JAVA_HOME`; do not upgrade project dependencies to match the host.
- **Hilt rewrites the bytecode** of `@AndroidEntryPoint` and `@HiltAndroidApp` classes, so `jacocoTestReport` reads the rewritten classes (`transformDebugClassesWithAsm`) and excludes Hilt's generated ones. Reading the compiler output instead makes those classes show 0% and fails SonarCloud (#71).
- **Kotlin interface defaults and coverage:** JaCoCo can count a legacy `DefaultImpls` bridge as an uncovered source line even when the default argument is exercised. For `MessageRepository`, all callers compile with the app and can use the interface's JVM default directly (#238).
- **Rules tests are CommonJS and run with `node` directly**, not through `npm` or as ES modules: the standalone Firebase CLI binary puts its own `node`/`npm` shims first in `PATH` inside `emulators:exec`, and they reject Node flags, npm scripts and ES modules.
- **Reaching the emulators from an Android emulator** needs two debug-only settings (`app/src/debug`): cleartext HTTP to `10.0.2.2` (the debug copy of `res/xml/network_security_config.xml` replaces the HTTPS-only one in `src/main`; keep `<application>` out of the debug manifest, where SonarCloud flags it as unsafe backup, rule `xml:S6358`) and, on Android 17 (API 37), the `ACCESS_LOCAL_NETWORK` permission, which `FirebaseEmulator` grants itself. Without them every request times out or is refused. Also, Espresso's accessibility checks bring the old `protobuf-lite`, which crashes Firestore in the test APK, so `app/build.gradle.kts` excludes it from instrumented-test configurations.
- **A freshly booted CI emulator is still busy:** Android can install our APKs late, during the first test, and restart its activity ("No compose hierarchies found", or a node "is not displayed"). So CI installs the APKs itself with Gradle (`installDebug installDebugAndroidTest`, with `connectedCheck`'s arguments, since `adb install` of the background build's APKs fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`) and waits for `am wait-for-broadcast-idle` before `connectedCheck`. The system image download sometimes arrives corrupted ("Error on ZipFile unknown archive"), so CI installs it with retries. If either still happens, re-run the failed job ([#192](https://github.com/swent-polysocial/PolySocial/issues/192)).
- **The Firestore emulator's wipe can fail with HTTP 500** (`{"error":{"code":500,"status":"UNKNOWN"}}`), mostly right after an offline or write test: the delete commit notifies a Listen stream that has already closed (`IllegalStateException: Stream is already completed` in `firestore-debug.log`). It is not a lock timeout (that answers 409). The next wipe succeeds, so `FirebaseEmulator` retries a 5xx a few times (#309).

### Map and location

- **Emulator location (#278):** use Android 12+'s fused provider before network so an emulator's injected fix is usable even when its network provider has no cell/Wi-Fi location. Only coarse permission is used; no valid fix still returns Unavailable within 15 s. Distance tests use `FakeLocationService`.
- **`NominatimGeocodingService` enforces Nominatim's 1 request/second limit only if it stays a singleton**; keep the map and geocoding providers behind their interfaces, as they may change.
- **Mapbox annotation groups:** one manager owns a normal source/layer plus an SDK-created drag source/layer, even with non-draggable markers. Native tests verify the matched pair stays shared as the event count changes; counting every circle layer as a separate manager is incorrect ([SDK source](https://github.com/mapbox/mapbox-maps-android/blob/v11.32.0/plugin-annotation/src/main/java/com/mapbox/maps/plugin/annotation/AnnotationManagerImpl.kt)).

## Open questions (don't guess, ask)

- **Association account deletion (#201):** associations can't delete their own `users/{uid}` (#161), and the deletion flow refuses them with the privacy contact. Who deletes an association account, its `associations/{uid}` and its events, and how, is not decided; ask before building it.
- **Event capacity (#121, second PR):** the schema and the own-registration query are decided (see "Registrations"). Refusing a full event in a transaction needs a counter on the event (for example `attendeeCount`), so the event update rule would let a student change only that field, by exactly ±1, with their own attendee document. That widens an organizer-only rule, so it needs a team decision; until then registering doesn't check the capacity. #131's "Going" count uses a `count()` query on the attendees for now; once a counter exists it could read it instead, so organizers could then lose `list` on attendees (agreed in [#274's review](https://github.com/swent-polysocial/PolySocial/pull/274)).
- **Shared privacy notice:** Mehdi will supply the private manual-deletion contact and confirmed controller/provider processing countries and safeguards for #103. Explicit draft placeholders are authorized for the school prototype; no actual country or protection guarantee is invented. Update `privacy_contact_email` and `privacy_notice_draft_body` when supplied, and collection/access text when #121 or #123 is enabled.
- **Mapbox production account:** the team must decide billing, usage thresholds and token rotation before release; the prototype keeps the current account/token.
- **Groups of a deleted event or last member:** deleting an event must also delete its groups, groupMembers and messages; ordinary last-member leave also leaves nested messages. #275 currently cleans only registrations. Account membership/marker cleanup and message author removal are implemented by #241 (see `docs/Group-Chat-Deletion.md`); event/last-member cleanup remains separate work.
- **"I'm going" in the rules (Ayoub, #244):** whether joining a group also requires an `attendees` document in the rules, or only in the app.
- **Groups of an ended event (#295):** starting or joining a group doesn't check that the event hasn't ended, unlike registering; accepted for now, as the detail hides Find a group once the event has ended (`isPast`, checked when the event is read or changes, so a detail left open across the end keeps it until then). A rule for it would deny after the reads, so it needs its own result first (see `write`'s KDoc in `FirestoreGroupRepository`).
- **Owner delete of `users/{uid}`:** the rules still let a client delete its own `users/{uid}` (the app never does), which leaves its public copy until `deleteAccount` runs; removing that rule is a separate team question (see "Profiles").
- **Association access to other public events:** [Ayoub confirmed](https://github.com/swent-polysocial/PolySocial/pull/93#issuecomment-6069094805) that #47's writes will build on #52's own-association-events read policy. Whether associations may also read students' public events remains a separate team question; keep the current policy until a team decision. Widening it would also expose students' UIDs (`createdBy`, `organizerIds`, `allowedUids`).
- **Association members and event drafts:** Figma has them, but there is no data model yet. How does an association find and add a student as a member, and what can each role do? Drafts are not in the `Event` model. Figma's first-admin/invite sentence on association setup waits for this too (Lucas kept the review-focused description, #257 review).
- **Events without an end time:** check-in (#22) and Find my group (#20) only work during the event. Which time window applies when `endTime` is not set?
- **Year field values:** the profile step offers BA1–BA6 and MA1–MA4 under "Year" (as in Figma and #34), but these are EPFL semesters, and there is no option for exchange or PhD students. Rename to "Semester" and/or add options?
- **Usernames (Sprint 5 PO, for the Sprint 6 backlog; #338):** the "Adding friends" story mentions finding a student by username, but none exist (the Figma v2 profile step had one, never built). Needs a unique name, a `usernames/{name}` → UID lookup that students can `get` but never list, claim/rename rules, a name for older profiles, and `deleteAccount` releasing it. Until then, friends are added by QR code only.
- **Friends beyond the two students (#338):** showing friends on a public profile, or common friends in matching, needs someone other than the pair to read a friendship; decide the rule (or a server-side count) with the public/private profile choice.

Add new ones here and in the Architecture Diagram's "Design decisions" section.
