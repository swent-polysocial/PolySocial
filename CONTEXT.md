# Project context

What a coding agent (or a new teammate) needs to know before starting a session and can't easily get from the code: the current state, the decisions that override older text, and the traps. Process rules live in `AGENTS.md`, the design in the wiki's [Architecture Diagram](https://github.com/swent-polysocial/PolySocial/wiki/Architecture-Diagram) (source: `docs/Architecture-Diagram.md`). **Keep this file short.** Only add what changes how someone should build things (see "Session context" in `AGENTS.md`).

## Current state

With no profile, non-EPFL accounts resume association setup even after reinstall; only EPFL accounts need the same-device marker to disambiguate student and association setup. This exception changes no backend access. Marker cleanup after durable association typing is housekeeping: a failed write reports `RetryNeeded` and retries on refresh without blocking pending/verified entry. Until #259/#261, incomplete setup opens the pending app and verified accounts open the existing app; an offline identity read preserves the pending app’s retry path.

- **Association setup review (#256):** the association name lives only in `associations/{uid}`; the private profile has an empty `displayName`, compatible with the 50-character student limit. A retry whose create already succeeded updates the identity with the latest submitted values. `model/association/AssociationValidation.kt` owns shared form validation and repository constants own the limits; #248 reuses them when rebased. Websites require HTTPS with a host and valid port, as #125 requires a valid URL.

This same-device routing hint stores no raw email/password and grants no permissions. Setup/navigation follow separately; #127 owns pending UI and #208 owns login.

- **Password recovery (#164):** the owner keeps email enumeration protection enabled. Request resets directly through `AuthRepository`; never fetch providers by email. All accepted requests show conditional inbox guidance, including unknown and Google-only addresses. The request preserves the auth session and login form. - **Privacy notice (#103):** Profile exposes a read-only Privacy & data entry alongside confirmed logout (#109). The app shell supplies its destination to `ProfileRoute`; a standalone profile without that destination hides the entry. The summary and dated full notice are bundled and need no data query, so they remain usable offline. - **Session cache (#156):** `FirestoreSession` owns the replaceable database; repositories resolve it per operation. Cleanup serializes callers and protects holder state across threads. Once started, termination and persistence removal run with a 10-second timeout despite caller cancellation, then propagate cancellation. Access fails through typed repository errors until cleanup succeeds; retry reuses the stopped instance for persistence removal. Offline persistence stays enabled between logouts. The team confirmed clear-before-sign-out with blocking Retry in [#177 review](https://github.com/swent-polysocial/PolySocial/pull/177#issuecomment-6168926664). Profile integration is provided by #109 below.

- **Profile logout (#109):** Profile offers Log out with confirmation. Its ViewModel clears Firestore persistence before `AuthRepository.logOut()`. `AppShell` removes active and saved tab stacks; `AuthFlow` resets Welcome Google state, login, sign-up, verification and profile-setup state before Welcome. Cleanup failure keeps the user signed in behind blocking Retry, as confirmed by the team in [#177 review](https://github.com/swent-polysocial/PolySocial/pull/177#issuecomment-6168926664). The cache lifecycle is provided by #156. [Shared Figma confirmation (#108)](https://www.figma.com/design/7Gt7tmy1ikpNyNBh1P6QdY/App-Mockup?node-id=673-118).

- **Session guard (#198)** (policy: "Session isolation" under Account deletion): `PolySocialApp.onCreate` starts the singleton `FirestoreSessionGuard` once, with an app-wide `SupervisorJob` scope on `Dispatchers.Main.immediate`, so a UID change blocks the cache inside Firebase's auth callback, before the clear starts. App start awaits `ensureSession(uid)` only before its profile read (signed-out and unverified starts read nothing), and its Retry runs the guard again. An unexpected failure while checking a change neither crashes nor is swallowed: the cache is blocked unless known to be empty and observation goes on, so app start's Retry recovers; only a missing Firebase app ends observation. Every repository already turned the blocked access (`IllegalStateException`) into its typed error (`SessionRepositoryFailureTest`). An install from before the guard has no stored owner, so its first launch with a signed-in student clears that student's cache once (their offline data comes back from the server); after that, the same account keeps its cache across restarts. Proof: `FirestoreSessionGuardTest` (every transition, failure, timeout, cancellation, concurrency), `SessionGuardCacheTest` (Robolectric, real disk cache across restarts) and `SessionGuardEmulatorTest` (emulator, through the auth listener).

- **Verification foundation (#31):** `AuthRepository` sends verification links with typed delivery/throttling failures and reloads the account plus a forced ID-token refresh before reporting verification. `VerifyEmailViewModel` restores per-UID resend deadlines (45 seconds after delivery, three minutes after throttling), handles browser-return/entry races and cancellation, and keeps deadlines across sign-out. Only timestamps are persisted; successful verification clears them. The screen and navigation came with [#99](https://github.com/swent-polysocial/PolySocial/pull/99) (see the next entry).

- **Auth entry and Verify Email (#30/#31/#87/#99, #74):** `AppStartViewModel` routes signed-out users to Welcome, retained unverified sessions to Verify Email (overriding restored auth navigation on cold start), and verified sessions through the profile check (Figma "App start · loading") to AppShell or the profile step; a failed read shows "App start · couldn't load profile" with Retry. Verified login calls `refresh()` instead of bypassing the profile check, and verification success uses the same check. Saving the profile step calls `onProfileCreated()`, which opens the app without reading the profile again (the save proves it exists). Browser return refreshes verification and the ID token; Continue retries manually. Back and Change address on Verify Email, and Back on the profile step, sign out and reset the auth forms. Per-UID resend deadlines (45 seconds after delivery, three minutes after throttling) survive sign-out and clear on verification; re-entry never automatically repeats a successful delivery. Wide, short windows use two columns. Saved signed-out forms survive recreation; sign-up saves the Auth display name and creates no Firestore profile. Google is wired on Welcome and Log in (#107); the association action remains unavailable.
- **Package** `com.polysocial`, minSdk 28, compile/target SDK 37, JVM 17. Dependencies use the version catalog `gradle/libs.versions.toml`. Today it has Compose, Navigation Compose, Firebase Auth + Firestore, `kotlinx-coroutines-play-services` (`Task.await()` for Firebase calls, so don't write your own bridge), Hilt (with KSP), Kaspresso, Robolectric and MockK (including the same-version Android artifact for #87 device tests). **Mapbox Maps Compose is added by #50; AndroidX Core supplies one-off location access (#51).**
- **Security Rules** `firebase/firestore/firestore.rules` **deny everything by default**. `users/{uid}` (#35) is owner-only for verified emails and protects `isAssociationVerified`; `uid` must match its document ID, `accountType` is `student` or `association` if set, and `uid` and `accountType` are fixed after creation. `displayName`, when present, is a string of at most 50 characters on create and update (#143), the app's `MAX_DISPLAY_NAME_LENGTH`, counted in UTF-16 units like the rule's `size()`. An association can't delete its own `users/{uid}` (it would then count as a student, #161); an admin deletes association accounts. Event reads (#52) allow students (verified `@epfl.ch` accounts whose `users/{uid}` isn't an association, #161; no profile or no `accountType` counts as a student) to read public events or private events listing their UID in `allowedUids`; a verified association can read only its own association events (`createdBy == auth.uid` and `isAssociationEvent == true`). Event writes (#47): a verified EPFL student, or a verified association, creates events with `createdBy == auth.uid` in `organizerIds`, every organizer also in `allowedUids` (so no co-organizer manages a private event they can't read), and the fields `validateNewEvent` checks (title, description, category) plus an optional `locationName` of at most 100 characters; a verified association always sets `isAssociationEvent` and no one else may, because its read rule only covers its own association events. Any organizer updates or deletes, but `createdBy` and `isAssociationEvent` are fixed once created. An association account is recognised by its `users/{uid}`, even with an `@epfl.ch` email. `associations/{uid}` (#126): see "Association profiles" below. All other collections and event subcollections remain denied. Emulator config is in `firebase.json` (Auth 9099, Firestore 8080).

## Decided design (follow this, even where an issue still says otherwise)

- **Recovery privacy (#164):** the re-enabled-protection decision supersedes the earlier provider-aware prototype. Figma's explicit missing-account/provider recovery states are archived, not implemented. Signup may still show duplicate-email feedback; Google sign-in follows the current owner-confirmed Firebase linking decision. A consumed reset link proves email ownership (the Auth emulator marks it verified); sending the request never signs in or bypasses normal app checks.

- **Map provider: Mapbox** (#50, agreed 2026-10-07). General provider/token policy lands with the map implementation: use the prototype signup public token through ignored `local.properties`, never a secret token, and a dedicated limited-scope token before production. The renderer is the UI-side SDK exception; geocoding remains Nominatim. Optional telemetry/geofencing starts disabled. Mapbox bills separately, so Firebase/Google Cloud budget alerts do not cover its usage.

- **Map renderer (#50):** `MapboxRenderer` is the UI-side SDK component; `MapViewModel` gets events only through injected `RepositoryMapEventSource`, adapting #49's live flow. Cached results stay usable and terminal errors permit Retry. Event-query Retry restarts the 14-day window without recreating the renderer; renderer Retry leaves the event listener and preview intact. After first map load, individual resource failures preserve cached areas; initial/style failures permit renderer Retry. Markers share one annotation group. Optional telemetry/geofencing starts disabled; attribution and its preference dialog stay accessible. The preview uses Zurich-local Today / Tonight / date labels and opens an event-ID placeholder until #112's real detail screen lands.
- **Google authentication (#106):** Credential Manager explicit button flow, with Firebase token validation and verified exact `@epfl.ch` checks before profile access. Reject other domains before Firebase account creation. The owner confirmed Firebase's automatic provider linking for EPFL Google accounts through EPFL SSO; use the returned UID without a dedicated collision outcome or client-side linking flow. Unexpected Firebase failures remain recoverable. OAuth setup and all signing SHA-1 fingerprints are documented in README; admin console configuration remains required. Google rejects uppercase domains and subdomains to match the current rules; it does not normalize the identity. A missing Web OAuth client in the private config fails compilation (`default_web_client_id`); CI Google sign-in remains blocked on stable signing in #137. Tokens and rejected identities are transient only.

- **Sign-in providers: email/password and Google only, no Microsoft** (#106, #107; Lucas, [#197 review](https://github.com/swent-polysocial/PolySocial/pull/197#pullrequestreview-5539093813)). Microsoft sign-in would need EPFL's admin to whitelist the app, which is unlikely (they haven't for Canva). Google is open to every app and goes through EPFL's SSO, so it proves ongoing ownership of the `@epfl.ch` address just as well. Students still need a verified `@epfl.ch` email (the rules check it); only email/password needs our Verify Email screen.

- **Google sign-in buttons:** Welcome and Log in share the unchanged pre-approved Google PNG through `GoogleSignInButton`, preserving the logo, font and aspect ratio. [Google requires compliant branding](https://developers.google.com/identity/branding-guidelines) for app verification; a plain-text or monochrome G is not allowed. The light pill is our selected supported variant, not a Google requirement to use only light buttons. Both actions run the same repository operation, disable competing navigation while loading, and use shared responsive error screens.

- **Layers:** Compose screen → ViewModel (one `StateFlow` UI state) → repository interface → Firebase/device implementation, with a `Fake…` implementation for tests. Pure logic (validation, haversine distance, filtering, matching, QR parsing) goes in plain Kotlin with no Android/Firebase imports.
  - Every screen that holds state has exactly one ViewModel. The app shell has none, because the `NavController` owns navigation state.
- **Failures are handled gracefully, everywhere.** Anything that can fail (Firebase, network, stored data with a missing or wrong-typed field, parsing, location, camera, permissions) returns a typed result from its repository or service (`…Result` with `NetworkError` / `UnexpectedError`), which the ViewModel shows as an error state with a way out (for example *Try again*). Nothing crashes the app or leaves a screen loading forever; the caller's cancellation always gets through (a cancelled Firebase task while the caller still runs is a failure, see `reportFailures`). Each failure path has a test. Rule in `AGENTS.md` → Architecture.
- **Names fixed by Sprint 1 issues:**
  - `AuthRepository`, returning a sealed Result per method: `logIn`, `logOut`, `currentUser` (#32); each issue adds its own methods, `signUp` (#30) and `sendVerificationEmail`, `reloadAndCheckVerified` (#31). **One ViewModel per screen** (e.g. `LoginViewModel`), not a shared `AuthViewModel` as the issues first said.
  - `UserProfileRepository` (`createProfile`, `getProfile`, `updateProfile`) on `users/{uid}` (#34). `UserProfile` holds `uid`, `email`, `displayName`, `section` and `year` (codes such as `IN`, `BA3`), `accountType` (`student` by default), `isAssociationVerified` (`false` unless it is the boolean `true`, like the rules, so a typo by the admin can't make the profile unreadable) and a server-set `createdAt`; `isVerifiedAssociation` combines the two account fields. Profile writes run in a **Firestore transaction**: it checks "create once" and "update only if it exists", and it fails offline (`NetworkError`) instead of queuing, so the profile step can show an error with Retry. The client never writes `isAssociationVerified`.
  - `EventRepository` (`createEvent`, `getUpcomingPublicEvents(windowDays)`, `getEvent`, `updateEvent`, `deleteEvent`, `getOwnAssociationEvents`) on `events/{id}` (#45, #49, #112, #130, #132).
  - `RegistrationRepository` (`register`, `cancel`, `observeMyRegistrations`) on `events/{eventId}/attendees/{uid}` (#121).
- **Profile created at the first verified entry**, not at sign-up. The rules require `email_verified`, so a write right after sign-up is denied. Create it exactly once, on Verify Email "Continue" or when app-start routing finds a verified user without a profile.
- **Anyone can create an event** and becomes its organizer. `Event.organizerIds` (always contains `createdBy`) controls who can manage it. Only a verified association (`accountType == "association"` and `isAssociationVerified`) publishes under its name: its events get `isAssociationEvent`, which shows a verified badge. An unverified association account can't create events or add members until it's verified. The Security Rules enforce this (#47 denies event creation from an unverified association). The app doesn't keep such accounts away from Create Event yet: every account sees the "+" (#110) except an unverified association, which #127 routes to its pending app (no "+"). A denied write reaches the app as `UnexpectedError`, so there is no access-denied state on Create Event.
  - **The creator is the only organizer for now.** Adding co-organizers needs a way to find other students, so it comes with "Public profiles and profile visibility". `organizerIds` and the rules (#47) already allow several.
  - **"Cancel event"** (Figma "Association · manage event") will delete the event (#129–#131, Sprint 3); there is no "cancelled" status yet.
- **Event fields** (`model/event`, #45): `title` is required and at most 80 characters. `description` may be blank and is at most 5000 characters (in line with Meetup and Eventbrite). #47's rules should use the same limits. `endTime` is optional and must be after `startTime` when set. The form treats an end time earlier than the start time as the next day (22:00 → 02:00). `capacity` is optional and at least 2 when set. `category` is one of Study, Sports, Culture, Party or Other (the Figma chips). When reading events (#49), a stored category the app doesn't know becomes `OTHER`, never a crash. `location` is plain lat/lng (`Coordinates`), not a map SDK type. `locationName` is the picked place's name (at most 100 characters; the form shortens a longer one without splitting an emoji), stored since #112 so the detail screen can show it; older events read it as blank. The event rules (#47, #102) cap it at 100 too. No address is stored, since the Figma detail shows only the name. Validation is the pure `validateNewEvent`, which compares the start time with the current minute.
- **Creating an event** (`EventRepository.createEvent`): `withCreator` makes the signed-in user the creator, the only organizer and the only allowed reader, and sets `isAssociationEvent` from the creator's profile. Values the form sends for these fields are ignored. The checks run in a fixed order (invalid, not signed in, offline), and offline returns `NetworkError` without starting a write, so Figma's offline error state can show. `FirestoreEventRepository` checks the connection with `NetworkMonitor.isOnline()` (`model/network`, a one-off check that needs working internet) and writes in a transaction, which only runs against the server, so a write is never queued offline. After the offline check it reads the creator's profile for the badge: a failed read returns `NetworkError` or `UnexpectedError` without writing, so a verified association never publishes without its badge, and a user without a profile gets no badge. The badge is only as trustworthy as the client, so #47's rules must allow `isAssociationEvent == true` only when the creator's `users/{uid}` is a verified association.
- **Editing and deleting an event** (`updateEvent(event)`, `deleteEvent(id)`, #130): any organizer, not only the creator. Same order as `createEvent` (an update is validated with `validateNewEvent` first, except a start in the past; then the ID, the signed-in user, offline → `NetworkError` without writing), then **one transaction** reads the stored event, checks the user is in its `organizerIds` and writes. **Started events stay editable:** `validateEventUpdate` refuses a start in the past only when it differs from the stored start, so a typo can be fixed during the event but no event can be moved into the past (agreed in [#213's review](https://github.com/swent-polysocial/PolySocial/pull/213)). The write is a Firestore `update`, not `set`, so fields `Event` doesn't hold (for example a future attendee count) survive an edit. **Deleting removes only `events/{id}`:** Firestore keeps subcollections, and once `events/{id}` is gone no client can read the event, so #121's rules ("for an event they can read") no longer let anyone delete its attendee documents. #121 must therefore extend `deleteEvent` to delete them before or with the event, in the same organizer-only operation, without giving students broader access. Reminders are local jobs (#180), so the reminder worker checks that the event still exists before notifying, rather than expecting the organizer to cancel them. Nothing else stores per-event data yet. An update keeps the stored `createdBy`, `organizerIds`, `allowedUids` and `isAssociationEvent` (`withOwnershipOf`), whatever the form sends; changing organizers or readers needs its own issue. Results: `NotFound` for a missing, malformed or unreadable event (a **denied read is `NotFound`**: reading a missing event is denied by #52's rule, and a private event must look missing); `NotOrganizer` for a non-organizer, nobody signed in, or a **write** the rules deny. Deleting an event that no longer exists is `NotFound`, not a success.
- **Reading events for the map** (`EventRepository.getUpcomingPublicEvents(windowDays = 14)`, #49): a live `Flow<PublicEventsResult>` backed by a Firestore snapshot listener, not a one-off read, so new events appear on the map by themselves. It emits `Events(events, fromCache)` on every change, including cached events while offline (`fromCache = true`), ends after an `Error`, and removes the listener when collection is cancelled. It is conflated: a slow collector gets only the latest result, and the final `Error` is never dropped (a full `callbackFlow` buffer used to lose it). "Upcoming" is the pure `isUpcomingPublicEvent`: public and starting from now (included) to now + `windowDays` (excluded), fixed when collection starts; events already started are not shown. Reading is the hand-written `eventFromFirestore`: an unknown category becomes `OTHER`, and a document missing a required field is skipped. The map (#50) adapts this flow in its own `MapEventSource`.
- **Event detail** (#112): `EventRepository.getEvent(id)` is a live `Flow<EventResult>` (snapshot listener with metadata changes, conflated, like #49). `Found(event, fromCache)`; `NotFound` for a missing, deleted, malformed or **denied** event (a denied private event looks like a missing one, so its existence isn't revealed; the flow then ends); `NotCached` when Firestore considers itself offline and never read it. While online, the detail loads for at most 10 s from the start of each read (`SERVER_ANSWER_TIMEOUT_MILLIS`, see Traps), then shows the offline "not saved" state with Retry. After the timeout the read keeps listening, so a late answer still shows the event; Retry replaces it with a new read (#194). `EventDetailViewModel` reads the `eventId` navigation argument and shows times in the device zone with an end-day offset ("+1 day"). **`fromCache` alone doesn't mean offline:** Firestore's first snapshot of a cached event comes from the cache even online, so the ViewModel shows the offline states only when `NetworkMonitor` also says offline (the same applies to any screen showing an offline banner from `fromCache`). The screen follows the reduced Figma frames "Event detail · Sprint 2", "· student event", "· loading", "· not found", "· offline" and "· offline, not saved" (section 03): no Share, ⋯, audience chip, group card, "I'm going" or reminder until their issues (#122, #123, #131); an association's event shows its name since #128 (see "Association names"). The screen reuses #145's `EventCategoryStyle`.
- **Event detail screen** (#112): each tab's graph has `tab.eventDetailRoute` (`<tab>/event/{eventId}`), so the tab an event is opened from stays selected and Back returns to it. Open it with `navController.navigate(tab.eventDetailRoute(id))`: the Events cards and "View event" after creating (#211) do; the map preview (#94) should too. The detail hides the app bar and the bottom bar and draws edge to edge (its Figma frames have its own header and action bar); taps during a navigation transition are ignored, so a double Back can't empty the stack. Closed issues keep their original text, so where one disagrees with this section, this section wins. #31 still names a shared `AuthViewModel`; follow "Names fixed by Sprint 1 issues" above.

- **Google entry (#107):** new verified Google users enter the existing profile form with name/email prefilled; existing users use the shared startup profile lookup. Error screens use two columns in wide, short windows, like Verify Email (#99), and Back returns to the original auth screen. Cancellation is silent. Google uses Firebase-managed account linking; no original-method error screen is shown. Unexpected failures offer Try again. The real profile form replaces the startup marker here and is shared with the Verify Email flow on main; navigation, verification, password recovery and logout reset behavior from main are preserved.

## Traps

- **Google picker context (#107):** the ViewModel coroutine can hold the initiating Activity until the repository operation returns or is cancelled, including across recreation. No Activity is stored in UI state or repository fields. Offline pending-attempt restoration tests do not prove real Credential Manager rotation behavior; that still needs device validation. ([#168](https://github.com/swent-polysocial/PolySocial/pull/168))

- **Logout navigation tests must retain the controller.** A fresh shell hides missed teardown. Assert the active stack is empty, then try restoring a previously saved tab on the same controller; `clearBackStack()` returning `false` after the active stack is empty does not prove there was no saved state. ([#177](https://github.com/swent-polysocial/PolySocial/pull/177))

- **Verification UI tests must wait for enabled Continue.** Initial email sending and lifecycle verification checks disable it; Compose idleness alone does not guarantee startup work has finished, and a click on a disabled button is ignored. Use observable UI conditions instead of sleeps. For callback/navigation checks, semantic click actions target Continue even when transient UI overlaps its touch coordinates ([#99](https://github.com/swent-polysocial/PolySocial/pull/99)).

- **The Firestore emulator doesn't enforce composite indexes.** A query missing from `firebase/firestore/firestore.indexes.json` still passes the emulator tests and only fails on the real backend. Add the index by hand and deploy it as the README says (#117).
- **A freshly booted CI emulator is still busy.** Android can handle the first install of our APKs several seconds late, during the first test, and restart that test's activity, which then fails with "No compose hierarchies found" (or a node "is not displayed"). Waiting for idle broadcasts before the install wasn't enough, so CI installs the APKs itself (`installDebug installDebugAndroidTest`) and waits for `am wait-for-broadcast-idle` before `connectedCheck`, whose own install is then an update. Inside the emulator step Gradle signs the APKs with another debug key than the background build, so that install must use Gradle with `connectedCheck`'s arguments, not `adb install` of the background build's APKs (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`). The system image download also arrives corrupted now and then ("Error on ZipFile unknown archive"), so CI installs it with retries before the emulator step. If either still happens, re-run the failed job ([#192](https://github.com/swent-polysocial/PolySocial/issues/192)).
- **`FirebaseFirestore.disableNetwork()` does not make transactions fail.** They still reach the server and succeed, so it can't test the "offline returns `NetworkError`" path of `FirestoreUserProfileRepository`. The emulator tests use airplane mode instead (`cmd connectivity airplane-mode enable`), which makes create and update return `NetworkError` after about 8 s (#119).
- **Compose coverage:** JaCoCo can count unreachable change-mask branches when a callback captures an unstable ViewModel parameter. Do not pad tests to hit compiler paths or exclude application code. Use meaningful recovery/lifecycle tests; for shared actions, consolidate callback ownership outside Compose (see [#168](https://github.com/swent-polysocial/PolySocial/pull/168)).

- **Auth completion effects leave with the screen.** System Back must keep sign-up and login in composition during submission and successful routing; otherwise the account can be created or signed in without reaching its destination. In-screen login Back/Create account are locked too; failures unlock navigation. Regression tests use deferred fake repositories ([#87](https://github.com/swent-polysocial/PolySocial/pull/87)). The profile step does the same while saving (#74).
- **Sign-out must reset what outlives the screen.** `AuthFlow`'s ViewModels belong to the activity. When the start destination moves to `Login` (a sign-out, from anywhere), `AuthFlow` resets the sign-up and log-in forms (a kept `SignedUp` or `LoggedIn` status redirects at once), verification (including pending checks and the previous email, while keeping per-account resend cooldowns), and the profile step (it holds the account's name and email). The same shared reset runs on explicit Profile logout and Verify Email Back/change address. Anything else that caches the signed-in account must be reset there too. A recreation replays the current destination, so `AuthFlow` remembers the last one it applied to tell the two apart (#74).

- **The signed-in apps' ViewModels can outlive the session.** `AuthFlow` isn't in a NavHost, so a `hiltViewModel()` it (or the pending association app) creates outside a nav entry belongs to the activity. The pending app therefore resets its logout state and forgets the association on Log out, and reads it again for each session; a log out then log in as another account without restarting must keep working (`PendingAssociationFlowTest`, [#127](https://github.com/swent-polysocial/PolySocial/issues/127)).
- **Uninstalling `AuthModule` in a Hilt test also drops the session guard's bindings.** `PolySocialApp`'s injector is part of every Hilt test component, even under `HiltTestApplication`, so such a test must `@BindValue` a `SessionGuard`, an `AuthSessionSource` and a `SessionOwnerStore` (fakes in `app/src/sharedTest`), or Hilt fails to compile. Under `HiltTestApplication` nothing starts the guard; a test that needs it starts it itself (#198).
- **A single-document `get(Source.CACHE)` never completed under Robolectric** (#198); `SessionGuardCacheTest` and `FirestoreCacheResetTest` read the cache with a collection query instead.
- **`onProfileCreated()` opens the students' app.** Fine while the profile step only creates students; when #125 creates association profiles there, route those to `PendingAssociation` ([#127](https://github.com/swent-polysocial/PolySocial/issues/127)).

- **Local Java version:** the host default Java 27 causes JaCoCo test instrumentation errors (`Unsupported class file major version 71`). Run Gradle with the installed Java 21 via `JAVA_HOME`; do not upgrade project dependencies to match the host.

- **Security Rules are not filters.** A query that could return a document the user can't read fails entirely. Public events need `where isPrivate == false`. Private events need `where isPrivate == true` and `array-contains` the signed-in UID on `allowedUids`. Association event queries need `createdBy == auth.uid` and `isAssociationEvent == true`; the association verification comes from its protected `users/{uid}` document, never client-supplied token claims. An association (whatever its email domain) cannot run the student map's unrestricted public query; its own-event browsing needs the owner-constrained query.
- **Private rules use `allowedUids.hasAny([auth.uid])`.** This list-only operation denies malformed map/string allowlists and supports `array-contains` queries. Adding a separate `allowedUids is list` check makes even the valid query fail in the emulator's rules evaluation.
- **Matching Figma in Compose** (found on the profile step, #34):
  - Lay a screen out with a `Column` and Figma's gaps as `Spacer`s, not at absolute Figma positions. Each half-dp gap is rounded to whole pixels, which can add up to a few dp down the screen; the team accepts that (review of [#95](https://github.com/swent-polysocial/PolySocial/pull/95)) over a custom layout tied to one frame size.
  - Give texts `TextMotion.Animated`: Android otherwise rounds each glyph to a whole pixel, so long texts come out about 1 dp narrower than Figma.
  - Multi-line texts with a line height need `LineHeightStyle(Center, Trim.None)`; Compose trims the first and last line by default, Figma doesn't.
  - Material's `DropdownMenu` keeps a 48 dp margin from the window edge and opens *above* a field near the bottom of an 800 dp screen; use a custom `Popup` when Figma shows it below.
  - Check on a device, not Robolectric (its text metrics differ): render the state, export the Figma frame at the device scale, and compare element by element.
  - Robolectric's default (legacy) graphics never draw an ellipsis and give every text line a fake height. A test of shortened text, exact heights or large font sizes needs `@GraphicsMode(GraphicsMode.Mode.NATIVE)`, ideally at the Figma frame's size (`@Config(qualifiers = "w360dp-h800dp")`) (#134).
- **Don't let Firestore map `Event` automatically** (`set(event)`, `toObject`). It stores the Kotlin property `isPrivate` as `private` (and `isAssociationEvent` as `associationEvent`), so queries and rules on `isPrivate` never match, and reading needs a no-argument constructor. Convert to and from a map by hand (writing: `Event.toFirestoreMap()`).
- `isPrivate == false` combined with a `startTime` range needs a **composite index**. It is versioned in `firebase/firestore/firestore.indexes.json` (#49), but it must also be **deployed** to the Firebase project (`firebase deploy --only firestore:indexes`), or the live query fails. The emulator doesn't need it.
- **Firestore queues writes while offline** instead of failing them, so a screen that waits for a write would spin forever. `EventRepository.createEvent` checks connectivity first and returns `NetworkError` (#45); any repository whose write the UI waits for must do the same.
- After the email is verified, **force an ID-token refresh** (`getIdToken(true)`), or the rules still see `email_verified == false`.
- Distance on the map is **straight-line** (haversine), labelled as such. Route-based distances are out of scope.
- **Hilt rewrites the bytecode** of `@AndroidEntryPoint` and `@HiltAndroidApp` classes, so `jacocoTestReport` reads the rewritten classes (`transformDebugClassesWithAsm`) and excludes Hilt's generated ones. Reading the compiler output instead makes those classes show 0% and fails SonarCloud. (#71)
- **A missing field makes a rule fail, not compare false.** `get(...).data.accountType == 'association'` errors, and so denies, when a student's profile has no `accountType`. Read optional fields with `data.get('field', default)` (#47).
- **Rules are deny-by-default since #35:** a new collection is unreachable, even in the emulator, until its own `match` block is added (#47, #52). Never bring back a broad `match /{document=**}`: Firestore allows access if any matching rule allows it, so it would reopen everyone's `users/{uid}`.
- **Rules tests are CommonJS and run with `node` directly**, not through `npm` or as ES modules: the standalone Firebase CLI binary puts its own `node`/`npm` shims first in `PATH` inside `emulators:exec`, and they reject Node flags, npm scripts and ES modules.
- **`fromCache` alone doesn't mean offline.** With metadata changes included, Firestore's first snapshot of cached data comes from the cache even online, until the server answers. A screen that maps `fromCache` straight to an offline banner makes it flash on most opens; show it only when `NetworkMonitor.isOnline()` is also false (review of [#145](https://github.com/swent-polysocial/PolySocial/pull/145), same rule as #152).
- **Firestore can stay silent about a missing document.** While it thinks it is online, it withholds the cached "missing document" snapshot of a never-read document until its own offline detection (about 10 s) or a stream failure, and it may emit nothing at all if the connection dies silently. A screen waiting for a server answer needs its own timeout from the start of the read (#194).
- **A tab screen that uses `hiltViewModel()` breaks tests that render `AppShell` or `AuthFlow`** in a plain `ComponentActivity` (no Hilt there). Both take the screen as a parameter with the real one as default (`AppShell(eventsContent = …)`, `AuthFlow(signedInContent = …)`), and those tests pass a placeholder; a new real tab adds its own parameter the same way (#105).
- **Reaching the emulators from an Android emulator** needs two debug-only settings (`app/src/debug`): cleartext HTTP to `10.0.2.2` (the debug copy of `res/xml/network_security_config.xml` replaces the HTTPS-only one in `src/main`; keep `<application>` out of the debug manifest, where SonarCloud flags it as unsafe backup, rule `xml:S6358`) and, on Android 17 (API 37) the `ACCESS_LOCAL_NETWORK` permission, which `FirebaseEmulator` grants itself. Without them every request times out or is refused. Also, Espresso's accessibility checks bring the old `protobuf-lite`, which crashes Firestore in the test APK, so `app/build.gradle.kts` excludes it from instrumented-test configurations.
- **A ViewModel that starts work in `init` binds `viewModelScope` at construction.** A test that creates it as a field, before `MainDispatcherRule` sets the test dispatcher, ties every later coroutine to the real Main dispatcher, so nothing the test advances runs (saves stay "Saving"). Create such ViewModels lazily or inside the test (#134).
- **Draw a shared composable once, above a `when`.** The same composable called in two branches is two different nodes, so switching branches recreates it: a text field loses its focus and cursor mid-typing. The Events search dropped letters when the list went from results to no match ([#178](https://github.com/swent-polysocial/PolySocial/pull/178)).
- **Material 3's date picker opens on the device's current month**, whatever the injected `Clock` says. A test that taps a day in the calendar depends on the real date; switch the dialog to text input mode and type the date instead (#136).
- **Association names (#128) recheck the account only when a collector starts and on each new name.** `CachedAssociationNames` is a singleton, so a screen that stays alive across an account switch would keep the previous account's names. Today the account only changes through logout, which clears every tab's back stack; keep it that way, or combine `names` with an auth-state flow ([#252](https://github.com/swent-polysocial/PolySocial/pull/252#issuecomment-6494137979)).
- **Emulators often have no location:** `AndroidLocationService` uses only the network provider, which was disabled on our API 37 emulator, so every read there is Unavailable. Test distance features with `FakeLocationService`, or on a phone (#115).
- **Map and geocoding providers may change**, so keep them behind the repository and service interfaces. Nominatim's policy allows explicit search only, at most 1 request per second, with a custom User-Agent and OSM attribution; `NominatimGeocodingService` enforces the rate limit only if it stays a singleton.

- **Mapbox annotation groups:** one manager owns a normal source/layer plus an SDK-created drag source/layer, even with non-draggable markers. Native tests verify the matched pair stays shared as event count changes; counting every circle layer as a separate manager is incorrect. ([SDK source](https://github.com/mapbox/mapbox-maps-android/blob/v11.32.0/plugin-annotation/src/main/java/com/mapbox/maps/plugin/annotation/AnnotationManagerImpl.kt))

- **Mapbox trial tokens:** card-free signup provides one token and currently allows 100 monthly active mobile users. Creating or rotating tokens requires adding a payment method. The default public token has broader public scopes than the dedicated production token; its value remains extractable from the app even though local config is ignored. See [signup limits](https://docs.mapbox.com/accounts/guides/signup/).

## Open questions (don't guess, ask)

- **Association account deletion (#201):** associations can't delete their own `users/{uid}` (#161), and the deletion flow refuses them with the privacy contact. Who deletes an association account, its `associations/{uid}` and its events, and how, is not decided; ask before building it.
- **Unverified accounts (#149):** the policy is decided (see "Account deletion" in Decided design). Only the implementation remains: #149's "Change address" deletion and 7-day cleanup, as new follow-up issues. Session loss (#198) is implemented (see "Session guard" in Current state).

- **Event capacity (#121, second PR):** the schema and the own-registration query are decided (see "Registrations"). Refusing a full event in a transaction needs a counter on the event (for example `attendeeCount`), so the event update rule would let a student change only that field, by exactly ±1, with their own attendee document. That widens an organizer-only rule, so it needs a team decision; until then registering doesn't check the capacity. The same counter would serve #131's "Going" count, so organizers could then lose `list` on attendees (agreed in [#274's review](https://github.com/swent-polysocial/PolySocial/pull/274)).
- **Deleted events (#121, #123):** `deleteEvent` (#130) removes only `events/{id}`. #121 must delete attendee documents before or with the event (in `deleteEvent`; organizers can now list them), and #123's worker must skip an event that no longer exists (see "Editing and deleting an event"); confirm with their owner, without broader student access or orphaned personal data.
- **Account-scoped reminders (#109, #123):** cancellation on logout and account deletion must keep a previous account's reminders out of the next session; cache isolation is decided (#198, see "Account deletion").
- **Profile recreated after deletion (#206, #207):** deleting the Auth user doesn't revoke ID tokens already issued (valid up to 1 h), and the rules let an owner create `users/{uid}`, so a client write still in flight after `deleteAccount` could recreate an orphaned profile with no Auth user. #207's client cleanup must clear the session cache before any further write; a periodic orphan cleanup would be a follow-up issue. Confirm with the team.
- **Shared privacy notice:** Mehdi will supply the private manual-deletion contact and confirmed controller/provider processing countries and safeguards for #103. Explicit draft placeholders are authorized for the school prototype; no actual country or protection guarantee is invented. Update `privacy_contact_email` and `privacy_notice_draft_body` when supplied, and collection/access text when #121 or #123 is enabled. Mapbox attribution and telemetry choices remain accessible from the Map.
- **Mapbox production account:** the team must decide billing, usage thresholds and token rotation before release; the prototype keeps the current account/token.

- **Association access to other public events:** [Ayoub confirmed](https://github.com/swent-polysocial/PolySocial/pull/93#issuecomment-6069094805) that #47's writes will build on #52's own-association-events read policy. Whether associations may also read students' public events remains a separate team question; keep the current policy until a team decision. Widening it would also expose students' UIDs (`createdBy`, `organizerIds`, `allowedUids`).
- **Association members and event drafts:** Figma has them, but there is no data model yet. How does an association find and add a student as a member, and what can each role do? Drafts are not in the `Event` model.
- **Events without an end time:** check-in (#22) and Find my group (#20) only work during the event. Which time window applies when `endTime` is not set?
- **Year field values:** the profile step offers BA1–BA6 and MA1–MA4 under "Year" (as in Figma and #34), but these are EPFL semesters, and there is no option for exchange or PhD students. Rename to "Semester" and/or add options?
- **Association validation shared between stacks (#125, #127):** the setup form (#256) and Edit details (#248) would validate the same fields twice, with different website checks (#256 also requires a host). Proposed in the [#256 review](https://github.com/swent-polysocial/PolySocial/pull/256#pullrequestreview-5696457857): whichever merges first owns it and the other reuses it. Lucas [answered](https://github.com/swent-polysocial/PolySocial/pull/256#issuecomment-6498630706) that #256's framework-free `model/association/AssociationValidation.kt` owns it and #248 reuses it; this closes once #248 confirms.
