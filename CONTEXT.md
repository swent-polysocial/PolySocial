# Project context

What a coding agent (or a new teammate) needs to know before starting a session and can't easily get from the code: the current state, the decisions that override older text, and the traps. Process rules live in `AGENTS.md`, the design in the wiki's [Architecture Diagram](https://github.com/swent-polysocial/PolySocial/wiki/Architecture-Diagram) (source: `docs/Architecture-Diagram.md`). **Keep this file short.** Only add what changes how someone should build things (see "Session context" in `AGENTS.md`).

## Current state

- **Password recovery (#164):** the owner keeps email enumeration protection enabled. Request resets directly through `AuthRepository`; never fetch providers by email. All accepted requests show conditional inbox guidance, including unknown and Google-only addresses. The request preserves the auth session and login form. Firebase handles password choice on its hosted action page.

- **Verification foundation (#31):** `AuthRepository` sends verification links with typed delivery/throttling failures and reloads the account plus a forced ID-token refresh before reporting verification. `VerifyEmailViewModel` restores per-UID resend deadlines (45 seconds after delivery, three minutes after throttling), handles browser-return/entry races and cancellation, and keeps deadlines across sign-out. Only timestamps are persisted; successful verification clears them. The screen and navigation remain in [#99](https://github.com/swent-polysocial/PolySocial/pull/99), which must merge after [foundation #186](https://github.com/swent-polysocial/PolySocial/pull/186).

- **Auth entry and Verify Email (#30/#31/#87/#99, #74):** `AppStartViewModel` routes signed-out users to Welcome, retained unverified sessions to Verify Email (overriding restored auth navigation on cold start), and verified sessions through the profile check (Figma "App start · loading") to AppShell or the profile step; a failed read shows "App start · couldn't load profile" with Retry. Verified login calls `refresh()` instead of bypassing the profile check, and verification success uses the same check. Saving the profile step calls `onProfileCreated()`, which opens the app without reading the profile again (the save proves it exists). Browser return refreshes verification and the ID token; Continue retries manually. Back and Change address on Verify Email, and Back on the profile step, sign out and reset the auth forms. Per-UID resend deadlines (45 seconds after delivery, three minutes after throttling) survive sign-out and clear on verification; re-entry never automatically repeats a successful delivery. Wide, short windows use two columns. Saved signed-out forms survive recreation; sign-up saves the Auth display name and creates no Firestore profile. Welcome's Google/association actions remain unavailable.
- **Package** `com.polysocial`, minSdk 28, compile/target SDK 37, JVM 17. Dependencies use the version catalog `gradle/libs.versions.toml`. Today it has Compose, Navigation Compose, Firebase Auth + Firestore, `kotlinx-coroutines-play-services` (`Task.await()` for Firebase calls, so don't write your own bridge), Hilt (with KSP), Kaspresso, Robolectric and MockK (including the same-version Android artifact for #87 device tests). **Mapbox Maps Compose is added by #50; AndroidX Core supplies one-off location access (#51).**
- **Security Rules** `firebase/firestore/firestore.rules` **deny everything by default**. `users/{uid}` (#35) is owner-only for verified emails and protects `isAssociationVerified`; `uid` must match its document ID, `accountType` is `student` or `association` if set, and `uid` and `accountType` are fixed after creation. An association can't delete its own `users/{uid}` (it would then count as a student, #161); an admin deletes association accounts. Event reads (#52) allow students (verified `@epfl.ch` accounts whose `users/{uid}` isn't an association, #161; no profile or no `accountType` counts as a student) to read public events or private events listing their UID in `allowedUids`; a verified association can read only its own association events (`createdBy == auth.uid` and `isAssociationEvent == true`). Event writes await #47; all other collections and event subcollections remain denied. Emulator config is in `firebase.json` (Auth 9099, Firestore 8080).
- **Setup:** the README's "Setup" section lists the two private, git-ignored files every clone needs: `local.properties` (SDK path) and `app/google-services.json` (Firebase config). CI creates both from GitHub secrets. `.gitignore` also covers keystores, `secrets.properties`, `.env` files and service-account JSON. Check that `git status` never lists them before committing.
- **Rules tests** live next to the rules (`firebase/firestore/firestore.rules.test.js`). They use `@firebase/rules-unit-testing` and Node's built-in test runner, with the npm packages pinned in `firebase/package.json` and its lockfile. The README has the command. CI runs them too (#159); rules PRs still paste the local output.
- **Mapbox setup (#50):** `MAPBOX_ACCESS_TOKEN` in git-ignored `local.properties` generates the SDK string resource. An empty token still builds and shows a setup state. See the README's Mapbox setup section.
- **Emulator tests** (#117) are instrumented tests in `app/src/androidTest/java/com/polysocial/emulator`, marked `@EmulatorTest`. `FirebaseEmulator` (a JUnit rule) connects its own `demo-polysocial` Firebase app to Auth and Firestore at `10.0.2.2`, clears both before each test, and signs in fictional verified users; the emulator applies the real Security Rules. `connectedCheck` skips them unless Gradle gets `-Pemulator` (only them) or `-Pemulator=all` (every instrumented test, as CI runs it). The README has the command.
- **CI** (`.github/workflows/ci.yml`, parallel since #192): "Checks" runs ktfmt, lint and the rules tests (pinned Firebase CLI, `firebase emulators:exec`). "Build and unit tests" builds the debug app and runs the unit tests. "Instrumented tests" runs `connectedCheck -Pemulator=all` in two shards (AndroidJUnitRunner `numShards`/`shardIndex`, each test runs once), each on its own API 34 `google_apis` emulator with **no camera**, inside the Auth and Firestore emulators, so the emulator tests run too. "Release build" runs alongside. "Coverage and SonarCloud" starts once the first three are done and works only from what they upload (unit `.exec` and JUnit XML, connected `.ec`, the Hilt-rewritten classes, lint XML), so a new file that JaCoCo or Sonar reads must be uploaded by the job that makes it. The required check `CI` passes only if every job succeeds, so a new job must be added to its `needs`. PRs that only change Markdown or `docs/` skip the build and test jobs.
- **Gradle** (#192): the build cache and the configuration cache are on, unit tests run in parallel forks (half the cores, at most 4) and the daemon heap is 4 GB. New build logic or plugins must work with the configuration cache.
- **PRs** must use `.github/pull_request_template.md`. Merges are **rebase merges**, so every commit lands on `main` as-is.
- **Scrum Board:** Product Backlog user stories are **draft items**, with no issue number. A Sprint task becomes a real **issue** when it is planned (course rule), so issue-numbered branches and `Closes #N` exist only for Sprint tasks. The fields are Task Type (Frontend / Backend / Figma, multi-select), Epic (dropdown), Priority (P0 high, P1 medium, P2 low) and Estimated / Actual Time (h) as numbers. Labels are GitHub's defaults only. The old user-story issues (#3–#28, #36) are closed, and their stories live on as drafts.

## Decided design (follow this, even where an issue still says otherwise)

- **Recovery privacy (#164):** the re-enabled-protection decision supersedes the earlier provider-aware prototype. Figma's explicit missing-account/provider recovery states are archived, not implemented. Signup may still show duplicate-email feedback; Google sign-in follows the current owner-confirmed Firebase linking decision. A consumed reset link proves email ownership (the Auth emulator marks it verified); sending the request never signs in or bypasses normal app checks.

- **Map provider: Mapbox** (#50, agreed 2026-10-07). General provider/token policy lands with the map implementation: use the prototype signup public token through ignored `local.properties`, never a secret token, and a dedicated limited-scope token before production. The renderer is the UI-side SDK exception; geocoding remains Nominatim. Optional telemetry/geofencing starts disabled. Mapbox bills separately, so Firebase/Google Cloud budget alerts do not cover its usage.

- **Map renderer (#50):** `MapboxRenderer` is the UI-side SDK component; `MapViewModel` gets events only through injected `RepositoryMapEventSource`, adapting #49's live flow. Cached results stay usable and terminal errors permit Retry. Event-query Retry restarts the 14-day window without recreating the renderer; renderer Retry leaves the event listener and preview intact. After first map load, individual resource failures preserve cached areas; initial/style failures permit renderer Retry. Markers share one annotation group. Optional telemetry/geofencing starts disabled; attribution and its preference dialog stay accessible. The preview uses Zurich-local Today / Tonight / date labels and opens an event-ID placeholder until #112's real detail screen lands.

- **Google sign-in buttons:** Welcome and Log in share the unchanged pre-approved Google PNG through `GoogleSignInButton`, preserving the logo, font and aspect ratio. [Google requires compliant branding](https://developers.google.com/identity/branding-guidelines) for app verification; a plain-text or monochrome G is not allowed. The light pill is our selected supported variant, not a Google requirement to use only light buttons. Actions remain unavailable until Google sign-in is implemented.

- **Layers:** Compose screen → ViewModel (one `StateFlow` UI state) → repository interface → Firebase/device implementation, with a `Fake…` implementation for tests. Pure logic (validation, haversine distance, filtering, matching, QR parsing) goes in plain Kotlin with no Android/Firebase imports.
  - Every screen that holds state has exactly one ViewModel. The app shell has none, because the `NavController` owns navigation state.
- **Failures are handled gracefully, everywhere.** Anything that can fail (Firebase, network, stored data with a missing or wrong-typed field, parsing, location, camera, permissions) returns a typed result from its repository or service (`…Result` with `NetworkError` / `UnexpectedError`), which the ViewModel shows as an error state with a way out (for example *Try again*). Nothing crashes the app or leaves a screen loading forever; the caller's cancellation always gets through (a cancelled Firebase task while the caller still runs is a failure, see `reportFailures`). Each failure path has a test. Rule in `AGENTS.md` → Architecture.
- **Names fixed by Sprint 1 issues:**
  - `AuthRepository`, returning a sealed Result per method: `logIn`, `logOut`, `currentUser` (#32); each issue adds its own methods, `signUp` (#30) and `sendVerificationEmail`, `reloadAndCheckVerified` (#31). **One ViewModel per screen** (e.g. `LoginViewModel`), not a shared `AuthViewModel` as the issues first said.
  - `UserProfileRepository` (`createProfile`, `getProfile`, `updateProfile`) on `users/{uid}` (#34). `UserProfile` holds `uid`, `email`, `displayName`, `section` and `year` (codes such as `IN`, `BA3`), `accountType` (`student` by default), `isAssociationVerified` (`false` unless it is the boolean `true`, like the rules, so a typo by the admin can't make the profile unreadable) and a server-set `createdAt`; `isVerifiedAssociation` combines the two account fields. Profile writes run in a **Firestore transaction**: it checks "create once" and "update only if it exists", and it fails offline (`NetworkError`) instead of queuing, so the profile step can show an error with Retry. The client never writes `isAssociationVerified`.
  - `EventRepository` (`createEvent`, `getUpcomingPublicEvents(windowDays)`) on `events/{id}` (#45, #49).
- **Profile created at the first verified entry**, not at sign-up. The rules require `email_verified`, so a write right after sign-up is denied. Create it exactly once, on Verify Email "Continue" or when app-start routing finds a verified user without a profile.
- **Anyone can create an event** and becomes its organizer. `Event.organizerIds` (always contains `createdBy`) controls who can manage it. Only a verified association (`accountType == "association"` and `isAssociationVerified`) publishes under its name: its events get `isAssociationEvent`, which shows a verified badge. An unverified association account can't create events or add members until it's verified. The Security Rules enforce this (#47 denies event creation from an unverified association). The app doesn't keep such accounts away from Create Event yet: every account sees the "+" (#110) until #127 routes unverified associations to their pending state. A denied write reaches the app as `UnexpectedError`, so there is no access-denied state on Create Event.
  - **The creator is the only organizer for now.** Adding co-organizers needs a way to find other students, so it comes with "Public profiles and profile visibility". `organizerIds` and the rules (#47) already allow several.
  - **"Cancel event"** (Figma "Association · manage event") will delete the event (#129–#131, Sprint 3); there is no "cancelled" status yet.
- **Event fields** (`model/event`, #45): `title` is required and at most 80 characters. `description` may be blank and is at most 5000 characters (in line with Meetup and Eventbrite). #47's rules should use the same limits. `endTime` is optional and must be after `startTime` when set. The form treats an end time earlier than the start time as the next day (22:00 → 02:00). `capacity` is optional and at least 2 when set. `category` is one of Study, Sports, Culture, Party or Other (the Figma chips). When reading events (#49), a stored category the app doesn't know becomes `OTHER`, never a crash. `location` is plain lat/lng (`Coordinates`), not a map SDK type. Validation is the pure `validateNewEvent`, which compares the start time with the current minute.
- **Creating an event** (`EventRepository.createEvent`): `withCreator` makes the signed-in user the creator, the only organizer and the only allowed reader, and sets `isAssociationEvent` from the creator's profile. Values the form sends for these fields are ignored. The checks run in a fixed order (invalid, not signed in, offline), and offline returns `NetworkError` without starting a write, so Figma's offline error state can show. `FirestoreEventRepository` checks the connection with `NetworkMonitor.isOnline()` (`model/network`, a one-off check that needs working internet) and writes in a transaction, which only runs against the server, so a write is never queued offline. After the offline check it reads the creator's profile for the badge: a failed read returns `NetworkError` or `UnexpectedError` without writing, so a verified association never publishes without its badge, and a user without a profile gets no badge. The badge is only as trustworthy as the client, so #47's rules must allow `isAssociationEvent == true` only when the creator's `users/{uid}` is a verified association.
- **Reading events for the map** (`EventRepository.getUpcomingPublicEvents(windowDays = 14)`, #49): a live `Flow<PublicEventsResult>` backed by a Firestore snapshot listener, not a one-off read, so new events appear on the map by themselves. It emits `Events(events, fromCache)` on every change, including cached events while offline (`fromCache = true`), ends after an `Error`, and removes the listener when collection is cancelled. It is conflated: a slow collector gets only the latest result, and the final `Error` is never dropped (a full `callbackFlow` buffer used to lose it). "Upcoming" is the pure `isUpcomingPublicEvent`: public and starting from now (included) to now + `windowDays` (excluded), fixed when collection starts; events already started are not shown. Reading is the hand-written `eventFromFirestore`: an unknown category becomes `OTHER`, and a document missing a required field is skipped. The map (#50) adapts this flow in its own `MapEventSource`.
- **Event detail** (#112): `EventRepository.getEvent(id)` is a live `Flow<EventResult>` (snapshot listener with metadata changes, conflated, like #49). `Found(event, fromCache)`; `NotFound` for a missing, deleted, malformed or **denied** event (a denied private event looks like a missing one, so its existence isn't revealed; the flow then ends); `NotCached` when offline and never read. `EventDetailViewModel` reads the `eventId` navigation argument and shows times in the device zone with an end-day offset ("+1 day"). **`fromCache` alone doesn't mean offline:** Firestore's first snapshot of a cached event comes from the cache even online, so the ViewModel shows the offline states only when `NetworkMonitor` also says offline (the same applies to any screen showing an offline banner from `fromCache`). The screen follows the reduced Figma frames "Event detail · Sprint 2", "· student event", "· loading", "· not found", "· offline" and "· offline, not saved" (section 03): no Share, ⋯, audience chip, group card, "I'm going" or reminder until their issues (#122, #123, #131); the association's name waits for #128. The screen reuses #145's `EventCategoryStyle`.
- **Event detail screen** (#112): each tab's graph has `tab.eventDetailRoute` (`<tab>/event/{eventId}`), so the tab an event is opened from stays selected and Back returns to it. Open it with `navController.navigate(tab.eventDetailRoute(id))`: the Events cards do, and the map preview (#94) and "View event" after creating (#110) should too. The detail hides the app bar and the bottom bar and draws edge to edge (its Figma frames have its own header and action bar); taps during a navigation transition are ignored, so a double Back can't empty the stack. It follows the reduced Sprint 2 frames in Figma section 03 (no Share, ⋯, audience chip, group card, "I'm going" or reminder until #122, #123 and #131; "Verified association" without the name until #128); "Find a group" shows a "not available yet" Snackbar.
- **Create Event screen** (`ui/event/create`, #46): the form logic is pure Kotlin (`CreateEventForm`). An error shows under its field once that field changes, and all errors show when Create is tapped with problems left; the button then stays disabled until they're fixed. An end time earlier than the start shows "+1 day". After creating, the "Event created" confirmation offers View event and Back to map. UI tests are Robolectric Compose tests in `app/src/test`, using `FakeEventRepository`. `CreateEventViewModel` is a `@HiltViewModel`. Classes that need the current time take a `java.time.Clock`, which `ClockModule` (`model/time`) provides unscoped, so each injection reads the device's current time zone; tests pass a fixed clock. The location picker opens through `onPickLocation` and is built in #111.
- **Private events** carry `allowedUids` (organizers, members, approved requesters). Rules check `allowedUids.hasAny([request.auth.uid])` (see "Traps" for why not `in`).
- **Location picker** (#111): geocoding is **Nominatim**, with the Mapbox map (#94; approved in `AGENTS.md`, free, OSM attribution already in Figma). `GeocodingService` (`model/geocoding`) offers `search` and `reverse`; `NominatimGeocodingService` checks `NetworkMonitor` first, waits 1 s between requests app-wide and caches answers in memory. A search is sent only on submit. The pin stays at the map center: dragging moves it and a tap recenters the map there; once the map settles (500 ms), the pin's name and address are looked up (reverse geocoding). An offline or failed lookup leaves the pin usable. The data layer and `LocationPickerViewModel` ship first (#150); the map screen follows on Mapbox.
- **Profiles are split.** `users/{uid}` is owner-only. `publicProfiles/{uid}` holds visible fields, with a public or private profile (Instagram-style). Section, year and interests are always visible (matching needs them).
- **Matching** is a deterministic heuristic (tag overlap / first-fit) in a pure module, run **on the device**. Group joins go through a Firestore transaction (capacity). A Cloud Function only if fairness or cheating becomes a problem.
- **Create Event** opens from a "+" button on the Events and Map tabs and follows the Figma (section 04, #44):
  - Fields: title, description, category, date with a start time and an **optional end time**, location (search or map pin), optional capacity, private or public. An end time earlier than the start time means the next day, and the form shows "+1 day" under the end field (Figma "Create event · overnight").
  - Validation errors inline (limits in "Event fields" above): missing title, title over 80 characters, description over 5000, past date, end time equal to the start time, missing location, capacity below 2.
  - After creating, an **"Event created" confirmation** offers *View event* and *Back to map* (team decision, 2026-10-06).
  - Offline, `EventRepository.createEvent` returns `NetworkError` without starting a write, and the ViewModel shows the offline error with *Try again*, keeping the form. If location access is denied, the picker still works with search and the map pin.
- **Events tab (#105):** lists the upcoming public events (`getUpcomingPublicEvents`) grouped by start day. Day headings are **Today / Tomorrow / the date** ("Sat 17 Oct"), not Figma's "Tonight" / "This weekend", which have no defined rules yet. Times are 24-hour, in the same time zone as the headings. The event detail comes with #112. The offline banner shows only when the events come from the cache **and** `NetworkMonitor` says offline (see Traps).
- **Event filter and search (#114):** the pure `filterEvents(events, filter, zone, userLocation)` (`model/event/EventFilter.kt`) filters the events **already loaded** by `getUpcomingPublicEvents`, so there is no new Firestore query or index, and it works offline on cached events. Search looks at the **title only**, ignoring case and accents. Several categories combine with OR, different criteria with AND. `DateRange` is start included, end excluded, read in the injected `Clock`'s zone. The maximum distance is straight-line (#51), an event exactly at it is kept, and **without a user location it is ignored** instead of hiding every event. `userLocation` has no default, so a caller can't drop the distance by forgetting it. The Events tab UI is #115.
- **Events tab search and filters (#115):** `EventsViewModel` keeps an `EventSelection` in its UI state and in `SavedStateHandle` (so it survives rotation), and runs `filterEvents` on the loaded events at every change. It holds the search, the categories, a `DateChoice` (Any, Today, This week until Sunday, or one `Day` picked among the next 14) and a maximum distance (500 m, 1 km or 2 km). The chip row and the Filters sheet apply each tap **right away**; "Show N events" only closes the sheet. *All* (like *Clear filters*) clears the search and the filters, as #113 decided; the sheet's *Clear* clears only the filters. The badge on the Filters button counts the date, the distance and each category.
  - **Location for the distance filter:** read **once**, only when a distance is picked and the permission is already granted, and kept in memory only. It is read only in the foreground, like the Map: leaving the tab cancels a read still running, and coming back reads again. Without the permission or a fix, the location is Off: the distance chips are disabled with Figma's note, and no distance stays selected. *Turn on* asks for coarse permission, or opens the app's settings once Android won't ask again. It shares the Map's "prompt requested" flag, and the tab rechecks the permission when it resumes.
- **Category look:** `ui/event/EventCategoryStyle.kt` gives each `EventCategory` its icon, label and colors (Figma: party red, sports green, culture blue, study amber; Other neutral). Reuse it on the map and Create Event instead of a second mapping, and show the label next to the color (Figma: never color alone).
- **Event filters** (Figma section 03, #113; logic #114, Events tab #115):
  - The Events and Map tabs keep **separate** selections, each in its own ViewModel.
  - The chip row has the quick filters (Today, This week, the categories); a **Filters sheet**, opened from the search field's sliders button, has them all: Date, Distance and Category.
  - Date: Any, Today, This week (until Sunday) or **one day** among the next 14 days, the window `getUpcomingPublicEvents` loads.
  - Distance (straight-line): Any, 500 m, 1 km or 2 km. Without the location permission the distance chips are disabled with *Turn on*, and the other filters still work.
  - Active filters show as chips with an ×, and the sliders button shows their count. *All* (Events) or *Clear filters* (Map) clears them in one tap. When nothing matches, the Events tab shows its empty state and the Map a "No matching events" card, both with *Clear filters*.
- **Chats:** a one-to-one chat is a two-member group (one model, one set of rules).
- **Find my group:** positions in `groups/{id}/locations/{uid}`, written only during the event, readable by members only, deleted afterwards. No location history.
- **Approved libraries (not added yet):** WorkManager for reminders: Event detail's "Remind me 1 h before" option schedules one 1 h before the start, and the notification permission is asked the first time it's turned on (#123). CameraX + ML Kit barcode scanning for QR codes, with typed payloads `polysocial://checkin/{eventId}/{token}` and `polysocial://friend/{uid}` checked by a pure parser.
- **Navigation:** one `NavHost` in `AppShell`, with string routes defined in the `Tab` enum (no typed routes, so no serialization plugin). Each tab is a nested graph (`tab.route`, starting at `tab.rootRoute`), so it keeps its own back stack (#42). Switching tabs uses Android's standard pattern (`popUpTo` the start destination with `saveState`, `launchSingleTop`, `restoreState`): the selected tab comes back on the screen it was on, Events stays at the bottom, so back from another tab's root goes to Events and back from the Events root exits. Each tab also has a placeholder detail route (`tab.detailRoute`; the Map's takes the event id, #50) until the event detail (#112) replaces it. **App bar actions (#84):** a tab's `action` (`TabAction`: Events → notifications, Chats → search chats, Profile → edit profile; Map has none, as in Figma) shows on the right of its app bar, **only at the tab root**, and opens `tab.routeOf(action)` inside the tab; each is a placeholder until its feature exists, which then replaces the placeholder at the same route. No unread dot until notifications exist. Every tab also has the event detail route (`tab.eventDetailRoute`, #112).
  - **Create Event (#110)** opens from the "+" on the Events and Map tabs, as a route in that tab's own graph (`tab.createEventRoute`), so Close and Back return to that tab; it shows full screen (no app bar or bottom bar, as in Figma). "Back to map" pops it before switching to the Map tab, so no tab comes back on the confirmation. "View event" replaces it with the tab's placeholder detail until #112, so Back skips the confirmation. On the map, `MapScreen` places the "+" itself (`onCreateEvent`), with the location button 12 dp above it, and hides it while an event card is open (Figma "Map" frames).
- **Tab loading state:** each tab root shows the shared `LoadingState` (`ui/common`) until its content is ready, then its content. Placeholder tabs use `PlaceholderTabViewModel` (`Loading` → `Placeholder`), one per tab, scoped to its navigation entry, so the loading state shows only on a tab's first visit. No artificial delay. The matching error state with Retry is the shared `ErrorState` (`ui/common`, Figma "Tab · couldn't load"), first used for the app start (#74). The Events tab is the first with real data (#105): its `EventsViewModel` replaces the placeholder one, and its error state can switch to the shared `ErrorState` in a follow-up.
- **DI: Hilt** (`@HiltViewModel`, constructor injection). Tests replace repositories with the `Fake…` versions through Hilt test modules. Set up in #70: `PolySocialApp` is the `@HiltAndroidApp` class, `MainActivity` is an `@AndroidEntryPoint`, and Compose gets ViewModels with `hiltViewModel()` (no navigation dependency needed). Each feature adds its own Hilt module for its repositories. `FirebaseModule` (`model/firebase`) provides the one `FirebaseFirestore`, which every Firestore repository takes as a parameter. Chosen after review over manual DI because it scales as repositories grow.
- **Signed-out navigation (#74):** Welcome, Sign up and Log in keep a small saved back stack in `AuthFlow`, so Back returns to the screen the user came from; opening a screen already in the stack goes back to it (Sign up and Log in link to each other). Verify Email, the profile step and the app clear it. Back on the profile step (arrow or system) signs out to Welcome, like Back on Verify Email in #99. Signing out goes through `AppStartViewModel.logOut()` alone, which also cancels a profile read in flight: `AuthFlow` reacts to the move to `Login` wherever it comes from, so Log out on the Profile tab (#109) and #99's Back only call it. The profile step is reset each time it opens, so a step left before (or already saved) never comes back half-done.
- **Back button:** at the root of the Map, Chats or Profile tab, back goes to the Events (home) tab, and at the Events root it exits (Android's standard). This overrides #42's current text.
- **Associations have no EPFL email** (SIC, Fréquence Banane… use their own domain, often from Google for nonprofits). They sign up with their own verified email and get **no access** until a PolySocial admin verifies them by setting `isAssociationVerified` by hand in the Firebase console (to be documented in the README). An in-app admin verification flow is in the backlog, not a current priority.
  - **Rules:** every granting rule needs `email_verified` **and** an `@epfl.ch` email on an account that isn't an association (students; an `@epfl.ch` association is still an association, #161) **or** a verified association (`accountType == "association"` and `isAssociationVerified`).
  - **Only exception:** any account with a verified email may read and write its own `users/{uid}`, but never set `isAssociationVerified`, on create or update, nor create it with an `accountType` other than `student` or `association`, nor change `uid` or `accountType` once created. That is all an unverified association can reach.
  - **What a verified association can do** (Figma): set up its association and see its profile, manage its members and their roles, and publish and manage its own events (Events tab: upcoming, drafts, past). No access to students' profiles, groups, chats or matching.
  - **In the app** (Sprint 3, moved out of Sprint 2 to keep it on the student flow for M1): an association gets its own tabs, Events, Map and Organization (#140), not the students' tabs. An unverified one sees them in their pending state (Figma "Association · pending review", #127). Its details (name, type, about, optional website) live in `associations/{uid}` (#126), and its logo is shown as initials until Cloud Storage uploads exist. Drafts, members and roles show "not available yet" until their data model is decided (see Open questions).
  - **Order of work:** #33 (PR #78) is students-only. #35 protects `isAssociationVerified` and removes the catch-all `match /{document=**}`, which let any EPFL user write someone else's `users/{uid}`. #52 builds on #35 for reads of an association's own events; event writes arrive with #47.
- **Section-exclusive events** are deferred.
- **Offline** relies only on Firestore's offline cache. No Room, no map tile prefetching, no Mapbox offline region downloads.
- **Not built yet:** an action Figma shows but the app doesn't support yet shows a "not available yet" Snackbar, never a broken screen (Milestone M1 requires the app not to misbehave).
- **Map location** (`model/location`, #51): `LocationService` performs one cancellable foreground fix (15-second timeout), uses only the declared coarse permission and network provider, and keeps coordinates in screen memory only. The Android implementation uses AndroidX Core's `LocationManagerCompat` without another dependency; only the permission-prompt flag is persisted. `MapRoute` launches the first-entry permission prompt; `MapViewModel` owns optional location states and pure haversine preview distance. Only coarse permission is requested. Permanent denial opens app settings; enabling permission there starts one fix on return. Leaving the foreground cancels requests and discards the snapshot into a quiet idle state; normal tab reentry never prompts or reads automatically again, but the floating refresh action can request another fix. Revocation hides badges without blocking events.

Closed issues keep their original text, so where one disagrees with this section, this section wins. #31 still names a shared `AuthViewModel`; follow "Names fixed by Sprint 1 issues" above.

## Traps

- **Verification UI tests must wait for enabled Continue.** Initial email sending and lifecycle verification checks disable it; Compose idleness alone does not guarantee startup work has finished, and a click on a disabled button is ignored. Use observable UI conditions instead of sleeps. For callback/navigation checks, semantic click actions target Continue even when transient UI overlaps its touch coordinates ([#99](https://github.com/swent-polysocial/PolySocial/pull/99)).

- **The Firestore emulator doesn't enforce composite indexes.** A query missing from `firebase/firestore/firestore.indexes.json` still passes the emulator tests and only fails on the real backend. Add the index by hand and deploy it as the README says (#117).
- **A freshly booted CI emulator is still busy.** Android can handle the first install of our APKs several seconds late, during the first test, and restart that test's activity, which then fails with "No compose hierarchies found" (or a node "is not displayed"). Waiting for idle broadcasts before the install wasn't enough, so CI installs the APKs itself (`installDebug installDebugAndroidTest`) and waits for `am wait-for-broadcast-idle` before `connectedCheck`, whose own install is then an update. Inside the emulator step Gradle signs the APKs with another debug key than the background build, so that install must use Gradle with `connectedCheck`'s arguments, not `adb install` of the background build's APKs (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`). The system image download also arrives corrupted now and then ("Error on ZipFile unknown archive"), so CI installs it with retries before the emulator step. If either still happens, re-run the failed job ([#192](https://github.com/swent-polysocial/PolySocial/issues/192)).
- **`FirebaseFirestore.disableNetwork()` does not make transactions fail.** They still reach the server and succeed, so it can't test the "offline returns `NetworkError`" path of `FirestoreUserProfileRepository`. The emulator tests use airplane mode instead (`cmd connectivity airplane-mode enable`), which makes create and update return `NetworkError` after about 8 s (#119).
- **Auth completion effects leave with the screen.** System Back must keep sign-up and login in composition during submission and successful routing; otherwise the account can be created or signed in without reaching its destination. In-screen login Back/Create account are locked too; failures unlock navigation. Regression tests use deferred fake repositories ([#87](https://github.com/swent-polysocial/PolySocial/pull/87)). The profile step does the same while saving (#74).
- **Sign-out must reset what outlives the screen.** `AuthFlow`'s ViewModels belong to the activity. When the start destination moves to `Login` (a sign-out, from anywhere), `AuthFlow` resets the sign-up and log-in forms (a kept `SignedUp` or `LoggedIn` status redirects at once) and the profile step (it holds the account's name and email). Anything else that caches the signed-in account must be reset there too. A recreation replays the current destination, so `AuthFlow` remembers the last one it applied to tell the two apart (#74).

- **Local Java version:** the host default Java 27 causes JaCoCo test instrumentation errors (`Unsupported class file major version 71`). Run Gradle with the installed Java 21 via `JAVA_HOME`; do not upgrade project dependencies to match the host.

- **Security Rules are not filters.** A query that could return a document the user can't read fails entirely. Public events need `where isPrivate == false`. Private events need `where isPrivate == true` and `array-contains` the signed-in UID on `allowedUids`. Association event queries need `createdBy == auth.uid` and `isAssociationEvent == true`; the association verification comes from its protected `users/{uid}` document, never client-supplied token claims. An association (whatever its email domain) cannot run the student map's unrestricted public query; its own-event browsing needs the owner-constrained query.
- **Private rules use `allowedUids.hasAny([auth.uid])`.** This list-only operation denies malformed map/string allowlists and supports `array-contains` queries. Adding a separate `allowedUids is list` check makes even the valid query fail in the emulator's rules evaluation.
- **Matching Figma in Compose** (found on the profile step, #34):
  - Lay a screen out with a `Column` and Figma's gaps as `Spacer`s, not at absolute Figma positions. Each half-dp gap is rounded to whole pixels, which can add up to a few dp down the screen; the team accepts that (review of [#95](https://github.com/swent-polysocial/PolySocial/pull/95)) over a custom layout tied to one frame size.
  - Give texts `TextMotion.Animated`: Android otherwise rounds each glyph to a whole pixel, so long texts come out about 1 dp narrower than Figma.
  - Multi-line texts with a line height need `LineHeightStyle(Center, Trim.None)`; Compose trims the first and last line by default, Figma doesn't.
  - Material's `DropdownMenu` keeps a 48 dp margin from the window edge and opens *above* a field near the bottom of an 800 dp screen; use a custom `Popup` when Figma shows it below.
  - Check on a device, not Robolectric (its text metrics differ): render the state, export the Figma frame at the device scale, and compare element by element.
- **Don't let Firestore map `Event` automatically** (`set(event)`, `toObject`). It stores the Kotlin property `isPrivate` as `private` (and `isAssociationEvent` as `associationEvent`), so queries and rules on `isPrivate` never match, and reading needs a no-argument constructor. Convert to and from a map by hand (writing: `Event.toFirestoreMap()`).
- `isPrivate == false` combined with a `startTime` range needs a **composite index**. It is versioned in `firebase/firestore/firestore.indexes.json` (#49), but it must also be **deployed** to the Firebase project (`firebase deploy --only firestore:indexes`), or the live query fails. The emulator doesn't need it.
- **Firestore queues writes while offline** instead of failing them, so a screen that waits for a write would spin forever. `EventRepository.createEvent` checks connectivity first and returns `NetworkError` (#45); any repository whose write the UI waits for must do the same.
- After the email is verified, **force an ID-token refresh** (`getIdToken(true)`), or the rules still see `email_verified == false`.
- Distance on the map is **straight-line** (haversine), labelled as such. Route-based distances are out of scope.
- **Hilt rewrites the bytecode** of `@AndroidEntryPoint` and `@HiltAndroidApp` classes, so `jacocoTestReport` reads the rewritten classes (`transformDebugClassesWithAsm`) and excludes Hilt's generated ones. Reading the compiler output instead makes those classes show 0% and fails SonarCloud. (#71)
- **Rules are deny-by-default since #35:** a new collection is unreachable, even in the emulator, until its own `match` block is added (#47, #52). Never bring back a broad `match /{document=**}`: Firestore allows access if any matching rule allows it, so it would reopen everyone's `users/{uid}`.
- **Rules tests are CommonJS and run with `node` directly**, not through `npm` or as ES modules: the standalone Firebase CLI binary puts its own `node`/`npm` shims first in `PATH` inside `emulators:exec`, and they reject Node flags, npm scripts and ES modules.
- **`fromCache` alone doesn't mean offline.** With metadata changes included, Firestore's first snapshot of cached data comes from the cache even online, until the server answers. A screen that maps `fromCache` straight to an offline banner makes it flash on most opens; show it only when `NetworkMonitor.isOnline()` is also false (review of [#145](https://github.com/swent-polysocial/PolySocial/pull/145), same rule as #152).
- **A tab screen that uses `hiltViewModel()` breaks tests that render `AppShell` or `AuthFlow`** in a plain `ComponentActivity` (no Hilt there). Both take the screen as a parameter with the real one as default (`AppShell(eventsContent = …)`, `AuthFlow(signedInContent = …)`), and those tests pass a placeholder; a new real tab adds its own parameter the same way (#105).
- **Reaching the emulators from an Android emulator** needs two debug-only settings (`app/src/debug`): cleartext HTTP to `10.0.2.2` (the debug copy of `res/xml/network_security_config.xml` replaces the HTTPS-only one in `src/main`; keep `<application>` out of the debug manifest, where SonarCloud flags it as unsafe backup, rule `xml:S6358`) and, on Android 17 (API 37) the `ACCESS_LOCAL_NETWORK` permission, which `FirebaseEmulator` grants itself. Without them every request times out or is refused. Also, Espresso's accessibility checks bring the old `protobuf-lite`, which crashes Firestore in the test APK, so `app/build.gradle.kts` excludes it from instrumented-test configurations.
- **Draw a shared composable once, above a `when`.** The same composable called in two branches is two different nodes, so switching branches recreates it: a text field loses its focus and cursor mid-typing. The Events search dropped letters when the list went from results to no match ([#178](https://github.com/swent-polysocial/PolySocial/pull/178)).
- **Emulators often have no location:** `AndroidLocationService` uses only the network provider, which was disabled on our API 37 emulator, so every read there is Unavailable. Test distance features with `FakeLocationService`, or on a phone (#115).
- **Map and geocoding providers may change**, so keep them behind the repository and service interfaces. Nominatim's policy allows explicit search only, at most 1 request per second, with a custom User-Agent and OSM attribution; `NominatimGeocodingService` enforces the rate limit only if it stays a singleton.

- **Mapbox annotation groups:** one manager owns a normal source/layer plus an SDK-created drag source/layer, even with non-draggable markers. Native tests verify the matched pair stays shared as event count changes; counting every circle layer as a separate manager is incorrect. ([SDK source](https://github.com/mapbox/mapbox-maps-android/blob/v11.32.0/plugin-annotation/src/main/java/com/mapbox/maps/plugin/annotation/AnnotationManagerImpl.kt))

- **Mapbox trial tokens:** card-free signup provides one token and currently allows 100 monthly active mobile users. Creating or rotating tokens requires adding a payment method. The default public token has broader public scopes than the dedicated production token; its value remains extractable from the app even though local config is ignored. See [signup limits](https://docs.mapbox.com/accounts/guides/signup/).

## Open questions (don't guess, ask)

- **Abandoned unverified accounts:** Back/change address leaves the Firebase account, so a mistyped address can block its owner's sign-up. [#149](https://github.com/swent-polysocial/PolySocial/issues/149) tracks the team decision on safe correction/deletion, recovery and retention; no automatic deletion policy is chosen here.

- **Attendance transaction (#121):** confirm the planned `events/{eventId}/attendees/{uid}` schema and how a student atomically checks capacity without reading other attendees or writing organizer-only event fields. Rules currently deny attendee access; agree this before implementation.
- **Account-scoped reminders (#109, #123):** cancellation on logout and cache isolation must keep a previous account's attendance/reminders out of the next session.
- **Shared privacy notice:** the supplied app mockup places it under Profile → Privacy & data, which is not implemented. Following Ayoub's #94 review and Mehdi's explicit instruction, remove the temporary Map privacy button; Mapbox attribution and telemetry choices stay accessible. The complete app notice is tracked in [#103](https://github.com/swent-polysocial/PolySocial/issues/103); Mehdi is now its assigned owner; the private manual-deletion contact and final wording must be confirmed before release.
- **Mapbox production account:** the team must decide billing, usage thresholds and token rotation before release; the prototype keeps the current account/token.

- **Association access to other public events:** [Ayoub confirmed](https://github.com/swent-polysocial/PolySocial/pull/93#issuecomment-6069094805) that #47's writes will build on #52's own-association-events read policy. Whether associations may also read students' public events remains a separate team question; keep the current policy until a team decision.
- **Sign-in providers:** add Google or Microsoft sign-in next to email/password? Every student account still needs a verified `@epfl.ch` email (checked by the rules). Only email/password needs our Verify Email screen, because Google and Microsoft deliver already-verified emails.
- **Association members and event drafts:** Figma has them, but there is no data model yet. How does an association find and add a student as a member, and what can each role do? Drafts are not in the `Event` model.
- **Events without an end time:** check-in (#22) and Find my group (#20) only work during the event. Which time window applies when `endTime` is not set?
- **Place name:** the Create Event form shows the picked place ("Rolex Learning Center"), but the event stores only coordinates. Should it also store a place name or address?
- **Uppercase or subdomain emails:** the rules deny `student@EPFL.CH` and `student@sub.epfl.ch` (#33). Revisit lowercasing the email (`.lower()`) if Google or Microsoft sign-in is added.
- **Year field values:** the profile step offers BA1–BA6 and MA1–MA4 under "Year" (as in Figma and #34), but these are EPFL semesters, and there is no option for exchange or PhD students. Rename to "Semester" and/or add options?

Add new ones here and in the Architecture Diagram's "Design decisions" section.
